# Tutorial: Managing Knowledgebases, Self-Healing OpenWiki & the Doc Studio

{/* kb:summary */}
This tutorial shows how to use Vox as a universal documentation and knowledgebase engine across single or federated polyglot repositories. You will configure the 3-layer Federated Knowledge Base, index source and documentation files with W3C SKOS facets and HippoRAG Personalized PageRank retrieval, generate 5-layer OpenWiki hubs with protected auto-fences, run Tier-1 and Tier-2 self-healing against code changes, and author Markdown, AsciiDoc, YAML, JSON, and CSV files in the non-modal Doc Dock.
{/* /kb:summary */}

Documentation fails for two predictable reasons: either it lives in an external wiki disconnected from code reviews and drifts out of date, or machine generators overwrite carefully written engineering explanations. Vox solves both problems together by combining a **3-layer Federated Knowledge Base**, **deterministic Polyglot Graphify + Personalized PageRank retrieval**, **5-layer OpenWiki generation with protected fences**, and a **two-tier self-healing loop** integrated directly beside the **Non-Modal Multi-Format Doc Studio** in Vox Axis.

## Understanding the 3-Layer Federated Knowledge Base

Vox separates durable shared engineering standards from repo-specific architecture and temporary cache shards so you can run Vox either inside the core Vox repository or across your own polyglot projects:

| Layer | Storage Location | Scope &amp; Git Policy | What Belongs Here |
|---|---|---|---|
| **Layer 1: Vox Baseline Canon** | `docs/src/` (canonical Vox canon) | Built-in / read-only baseline | Language grammar, durable workflows, `VoxDb`, MCP contracts, governance ADRs |
| **Layer 2: Global Library** | `~/.vox/library/` | User-global across every repo | Cross-project playbooks, promoted findings, reusable checklists &amp; standards |
| **Layer 3: Repo-Local Wiki** | `docs/wiki/` + `.vox/cache/` (or `--read-only` `~/.vox/repos/<id>/`) | Tracked Markdown + gitignored shards | Repo OpenWiki 5-layer hubs, local architecture decisions, symbol citations |

<Aside type="note" title="Zero-Footprint Read-Only Onboarding">
  Need to search, map, and generate an OpenWiki for an upstream third-party repository without writing `.vox/` or `docs/wiki/` files into its checkout? Pass `--read-only` when initializing or adding it — all indexes and OpenWiki caches stay isolated under `~/.vox/repos/<id>/`.
</Aside>

## Step-by-Step Guide

<Steps>

1. **Onboard Any Repository &amp; Federate Sibling Projects (`vox repo`)**

   Inside any Rust, TypeScript/JavaScript, Python, Go, Vox, or mixed repository, scaffold the harness (`VOX.md`, `AGENTS.md`, `.voxignore`, `.well-known/llms.txt`, `docs/wiki/`, and `.vox/repositories.yaml`), then federate sibling or upstream reference repositories:

   <Tabs>
     <TabItem label="CLI">
       ```bash
       # Initialize the current repository's KB, OpenWiki, and .vox/repositories.yaml
       vox repo init --name my-service

       # Or onboard an external reference repo with zero working-tree writes
       vox repo init --read-only

       # Register a sibling repository and an upstream read-only reference
       vox repo catalog refresh --add ../payments-worker --name "Payments Worker"
       vox repo catalog refresh --add ../upstream-sdk --name "Upstream SDK" --read-only

       # List cataloged repos, switch live daemon focus, or search code across repos
       vox repo catalog list
       vox repo catalog refresh --switch payments-worker
       vox repo query text "IdempotencyKey"
       ```

       Example `.vox/repositories.yaml` committed in the primary workspace:

       ```yaml
       schema_version: 1
       primary_repository_id: my-service
       repositories:
         - repository_id: my-service
           display_name: "My Service"
           root: "."
           read_only: false
         - repository_id: payments-worker
           display_name: "Payments Worker"
           root: "../payments-worker"
           read_only: false
         - repository_id: upstream-sdk
           display_name: "Upstream SDK"
           root: "../upstream-sdk"
           read_only: true   # shards stay isolated in ~/.vox/repos/upstream-sdk/
       ```
     </TabItem>
     <TabItem label="Vox Axis GUI">
       1. Open the **Repository** surface (`repository`) or click the persistent **Repo Switcher** in the bottom status bar.
       2. Register sibling repos via the onboarding panel with **Hybrid (`docs/wiki/`)** or **Read-Only External (`~/.vox/repos/`)** storage mode.
       3. Switching active repositories updates `active_repository_id` live in `vox-orchestrator-d` without restarting the app or leaking `repo_local` shards across projects.
     </TabItem>
   </Tabs>

2. **Author Structured Pages with W3C SKOS Facets &amp; Hybrid Graphify Search (`vox kb` + `VoxGraph`)**

   Every curated page carries machine-checkable YAML frontmatter bound to `contracts/documentation/kb-taxonomy.v1.yaml` (`category`, `status: "current"`, `topic`, `domain`, `authorship`) and a 40–120 word `<!-- kb:summary -->` directly under the H1 heading. When indexed, `vox-search` fuses four retrieval legs through Reciprocal Rank Fusion (RRF):

   1. **Tantivy BM25 lexical search** over heading chunks (`chunk_hash`, heading paths, `kb://` URIs)
   2. **HNSW semantic vector retrieval**
   3. **Polyglot Graphify AST + Doc + Decision cross-edges** (`documented_in`, `cites_symbol`, `governed_by_adr`)
   4. **HippoRAG Personalized PageRank (PPR) &amp; Leiden community summaries** — resolving multi-hop questions across code and documentation with zero upfront LLM indexing cost

3. **Generate a 5-Layer Polyglot OpenWiki with Human-Safe Auto-Fences (`vox ci wiki-sync`)**

   Run OpenWiki generation to synthesize five structured system layers for your codebase — covering module architecture, CLI/HTTP/MCP/API interfaces, SQL/VoxDb data models, GUI surfaces, and workflows/runbooks — complete with validated `vox-diagram` topologies:

   ```bash
   # Preview or initialize docs/wiki/ structure + .vox/cache/openwiki/manifest.v1.json
   vox ci wiki-sync --polyglot --init

   # Write/refresh all 5 OpenWiki layers deterministically
   vox ci wiki-sync --polyglot --write

   # Inspect repository OpenWiki status or diff without writing
   vox repo status --wiki status
   vox ci wiki-sync --polyglot --diff
   ```

   Crucially, OpenWiki isolates machine-maintained symbol tables, source `#Lstart-Lend` citations, and dependency diagrams inside deterministic fence markers so your surrounding architectural prose, design rationale, and runbooks are **never overwritten**:

   ```markdown
   ---
   title: "Layer 2 — API, CLI & MCP Interfaces"

   # Layer 2 — API, CLI & MCP Interfaces

   <!-- kb:summary -->
   Documents the HTTP, CLI, and MCP contracts exposed by my-service, pairing architectural notes maintained by engineers with automatically refreshed symbol signatures and source line anchors regenerated cleanly inside deterministic OpenWiki auto-fences.

   Keep custom rollout caveats, SLO thresholds, and deprecation warnings right here. Repeated `vox ci wiki-sync --polyglot --write` runs leave every word outside auto-fences untouched.
   ```

4. **Run Two-Tier Self-Healing When Code Changes (`--heal` &amp; Self-Heal Diff Inspector)**

   Whenever source files change, Vox runs two complementary healing tiers over Graphify's reverse `documented_in` / `cites_symbol` / `governed_by_adr` blast radius rather than scanning unrelated documentation:

   - **Tier 1 (Zero-LLM Deterministic AST Auto-Heal):** Traces `git diff` impact and updates shifted `#Lstart-Lend` anchors, function/struct signatures, CLI/MCP tables, and `vox-diagram` graphs inside `openwiki:auto` fences with `0` LLM calls:

     ```bash
     vox ci wiki-sync --polyglot --heal
     ```

   - **Tier 2 (4-Gate Verified Semantic Prose Proposals):** When behavior changes invalidate surrounding narrative prose, `vox audit docs --verify-llm` and `vox audit docs --self-heal-plan` synthesize minimal unified diffs via `vox_actor_runtime::llm` and gate every patch through **four checks** — `kb_rewrite_guard` anti-hallucination check, `vox-doc-pipeline --lint-only`, `vox-diagram` verification, and `.vox` doctest compilation — before staging approved diffs in `kb_heal_proposals` (`Apply Patch`, `Edit`, `Demote`, or `Reject`):

     ```bash
     vox audit docs --verify-llm
     vox audit docs --self-heal-plan
     vox ci wiki-sync --polyglot --heal --auto-apply
     ```

   Inspect how Tier-1 and Tier-2 cooperate on a concrete function rename + parameter addition:

   <Tabs>
     <TabItem label="1. Code Diff (src/billing.vox)">
       ```diff
       -tool "Charge invoice" charge_invoice(id: Id[Invoice]) to Result[str] {
       +tool "Charge invoice with idempotency key" charge_invoice(id: Id[Invoice], key: str) to Result[str] {
            return Ok("charged:" + key)
        }
       ```
     </TabItem>
     <TabItem label="2. Tier-1 Auto-Fence (0 LLM)">
       ```diff
        ## Human Engineering Context (Never Overwritten)
        Keep custom rollout caveats and SLO thresholds right here.

        <!-- openwiki:auto:start id="interface-inventory" -->
       -| `charge_invoice(id: Id[Invoice])` | MCP Tool | `src/billing.vox#L14-L18` |
       +| `charge_invoice(id: Id[Invoice], key: str)` | MCP Tool | `src/billing.vox#L28-L34` |
        <!-- openwiki:auto:end -->
       ```
     </TabItem>
     <TabItem label="3. Tier-2 4-Gate Prose Diff">
       ```diff
       -Call `charge_invoice` with an invoice id only; duplicate retries are unchecked.
       +Pass a caller-generated `key` (`[src/billing.vox:L28-L34]`) so `charge_invoice` enforces idempotent billing retries.
       ```
     </TabItem>
   </Tabs>

## Common Pitfalls &amp; Operational Recipes

<details open class="vox-details-card">
  <summary class="vox-details-summary">
    Keeping Federated Wikis &amp; Self-Healing Pipelines Clean
  </summary>
  <div style="margin-top: 0.85rem; font-size: 0.94rem; line-height: 1.58;">
    <ul>
      <li><strong>Do not hand-edit inside <code>openwiki:auto</code> fences:</strong> Any edits between <code>&lt;!-- openwiki:auto:start --&gt;</code> and <code>&lt;!-- openwiki:auto:end --&gt;</code> are overwritten on the next <code>vox ci wiki-sync</code> pass. Write team rationale strictly outside those markers.</li>
      <li><strong>Keep every <code>&lt;!-- kb:summary --&gt;</code> within 40–120 words:</strong> <code>vox-doc-pipeline --lint-only</code> enforces word bounds directly below the page H1 so retrieval snippets remain dense and consistent across <code>voxlang.org</code> and Axis Memory.</li>
      <li><strong>Use <code>--read-only</code> for third-party vendor checkouts:</strong> Keeping <code>{'read_only: true'}</code> stores Graphify and Tantivy shards strictly in <code>~/.vox/repos/&lt;id&gt;/</code> with zero untracked files in upstream checkouts.</li>
    </ul>

</details>

## Interactive Lab: Modeling a Self-Healing Wiki Registry in `.vox`

You can expose custom knowledgebase rules or team wiki validators as first-class Vox schemas, server handlers, and MCP tools in a single `.vox` module. Try editing and running the example below:

<VoxPlayground initialCode={`// Typed OpenWiki inventory + staleness check + MCP lookup tool in .vox
table WikiPage {
    slug:       str
    layer_num:  int
    needs_heal: bool
}

query stale_page_count() to int {
    return len(db.WikiPage.where({ needs_heal: true }))
}

server register_wiki_page(slug: str, layer_num: int, needs_heal: bool) to Result[str] {
    if layer_num < 1 or layer_num > 5 {
        return Error("OpenWiki layers must be between 1 and 5")
    }
    let _id = db.WikiPage.insert({ slug: slug, layer_num: layer_num, needs_heal: needs_heal })?
    return Ok("Registered layer " + str(layer_num) + " page: " + slug)
}

tool "Inspect OpenWiki staleness summary" wiki_health_report() to Result[str] {
    let total = len(db.WikiPage.all())
    let stale = stale_page_count()
    return Ok("OpenWiki pages=" + str(total) + " pending_heal=" + str(stale))
}

fn main() to Result[str] {
    print(register_wiki_page("layer-1-architecture", 1, false)?)
    print(register_wiki_page("layer-2-mcp-contracts", 2, true)?)
    let summary = wiki_health_report()?
    print(summary)
    return Ok(summary)
}`} />
