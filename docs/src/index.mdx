table Task {
    title: str
    done:  bool
}

query get_tasks() to int {
    return len(db.Task.all())
}

tool "Done" complete_task(id: Id[Task]) to Result[str] {
    db.Task.delete(id)?
    return Ok("done")
}

component TaskBoard() {
    view: column(raw_class="task-card") {
        heading(level=3) { "Active Tasks" }
        text() { "Synchronized across SQL, Rust, and React" }
    }
}

fn main() to Result[str] {
    let id = db.Task.insert({ title: "Write Vox in browser", done: false })?
    print("Tasks queued: " + str(get_tasks()))
    let status = complete_task(id)?
    print("Tasks remaining: " + str(get_tasks()))
    return Ok(status)
}`} />

## Why Vox

A typical web app restates one domain model in four places:

1. A **database schema** (SQL or an ORM migration).
2. A **backend** (Rust, Go, Python, or Node) that validates and serves it.
3. A **wire contract**, usually JSON.
4. A **frontend** (TypeScript/React) that reads that JSON.

Names and types can drift at each boundary. People and coding agents both spend time keeping the copies aligned.

<div align="center">
  <img src="./assets/schema-fragmentation.webp" alt="One field written four times: SQL completed_at, Rust Option DateTime, JSON completedAt null, and TypeScript isDone, beside one Vox table that emits done: bool to every layer" width="760" height="424" loading="lazy" decoding="async" />
  <p>
    <strong>One field, written four times</strong><br />
    <em>completed_at, completedAt, and isDone are the same fact. Each boundary renames it or changes its type. A Vox table states it once, and every layer keeps that name and type.</em>
  </p>
</div>

These are the choices that follow from that, and what each one buys.

**One declaration, projected.** A second schema, written by hand, drifts, and an agent copying it drifts the same way. A `table` is the source. SQL, the server types, the JSON shape, and the TypeScript client are generated from it. `vox build` emits SQLite/Turso, Rust (Axum), and React/TypeScript, because one stack is what the tests can actually cover. Django, Vue, and other frameworks are outside that path.

**Missing values and failures are typed.** Generated code skips a failure it cannot see. `Option[T]` is `Some(x)` or `None`. `Result[T]` is `Ok(x)` or `Error(msg)`. Code that ignores either case does not type-check. `?` returns the error to the caller.

**Ids are typed.** A task id and a user id are different facts. A boundary takes `Id[Task]` rather than a bare string, so the two cannot be swapped.

**Keywords open scopes. Decorators modify them.** `table`, `query`, `mutation`, `server`, `component`, `workflow`, `activity`, `tool`, and `resource` each open a scope. `@auth`, `@pure`, `@durable`, and `@uses` change how a declaration runs. One spelling means people and agents copy the same form. A new behavior is a decorator, so the keyword list stays stable.

**The same file runs now, or compiles.** Scripts, repo automation, and the browser playground should start without a Rust build. A shipped app should be ordinary Rust and TypeScript. `vox run` interprets the file. `--caps` is the list of effects the host grants (filesystem, network, and the rest). `vox build` emits the database, the server, and the client from that same file. The two executors are still being matched, and a generated server build needs a Vox source checkout (`VOX_REPO_ROOT`).

**A tool is a function in the same file.** An agent tool kept in a side schema drifts like a hand-written JSON contract. `tool` is a typed function plus a short description. The program and an MCP client call that declaration, and a failure comes back as `Result`.
{/* SYNC-END: why_vox */}

<details class="vox-details-card">
  <summary class="vox-details-summary">
    What do <code>Option[T]</code> and <code>Result[T]</code> mean if I'm coming from Python or JavaScript?
  </summary>
  <div style="margin-top: 0.75rem; font-size: 0.95rem; line-height: 1.6;">
    <p>In JavaScript or Python, any variable might secretly be <code>null</code>, <code>undefined</code>, or <code>None</code>, causing runtime crashes under edge inputs.</p>
    <ul>
      <li><strong><code>Option[T]</code></strong> encodes an explicitly optional value (<code>Some(value)</code> or <code>None</code>); the compiler rejects unchecked dereferences.</li>
      <li><strong><code>Result[T]</code></strong> encodes fallible operations (<code>Ok(value)</code> or <code>Error(message)</code>). Appending <code>?</code> unwraps <code>Ok</code> or propagates <code>Error</code> early.</li>
    </ul>
    <p style="margin-bottom: 0;">Read more in the <a href="/reference/ref-syntax/">Syntax Reference</a> or select <strong>"2. Safe Errors (Result[T])"</strong> in the sandbox above.</p>

## Ecosystem Separation of Concerns (`vox-foundation`)

To keep incremental Rust compile times fast, isolate frontend and documentation toolchains, and enforce a strict air-gap around optional remote telemetry while keeping `vox` **100% standalone offline**, the suite is federated across four repositories governed by `README-SYNC-MAP` and `vox ci cross-repo-parity` (56 `BLAKE3`-verified shared schemas):

## Tradeoffs & Current Stability (Progressive Deep Dive)

We grade every Vox surface honestly by what works today versus what is still a research prototype. Expand either table below when evaluating Vox for a project:

<details open class="vox-details-card">
  <summary class="vox-details-summary">
    When Vox Fits (and When You Should Pick Another Tool)
  </summary>
  <div style="margin-top: 0.85rem;">

| Tradeoff | Why You Might Like Vox | Why You Might Wait or Pick Another Tool |
|:---|:---|:---|
| **Opinionated Stack vs. Bring-Your-Own Framework** | You want one `.vox` file to generate your database schema, backend API, reactive UI, and MCP tools without wiring up four separate frameworks. | Full-stack codegen targets **Rust (Axum) + React 19 / TypeScript + SQLite/Turso**. If you need a Python/Go backend or Vue/Svelte frontend, Vox won't emit it. |
| **Compile-Time Strictness vs. Loose Scripting** | Every possible failure (`Result[T]`) and optional value (`Option[T]`) is checked before the program runs — catching bugs that LLMs and humans often miss. | You must handle `Ok`/`Error` and `Some`/`None` explicitly instead of writing quick untyped code that ignores errors. |
| **Interpreter vs. Full-Stack Codegen** | `vox run` runs scripts immediately with zero Rust compile wait and `--caps` sandboxing; `vox build` emits native Rust and TypeScript. | Compiling a generated Rust server outside the Vox repo currently requires building `vox` from a local source checkout (`VOX_REPO_ROOT`). |
| **Pre-1.0 Research Velocity vs. Long-Term Stability** | You can inspect an active AI-native language, 33-surface operator workbench (`Vox Axis`), and QLoRA evaluation lab with candid in-tree audits. | Vox is **pre-1.0 prototype software**. Syntax and CLI flags still evolve, and there are no prebuilt binary releases yet. |

  </div>
</details>
