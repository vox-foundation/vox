# Phase 24 Technical Research: Reader Trust Signals, Agent Surfaces & v1.4 Go/No-Go

## Executive Summary

Phase 24 is the capstone phase of the `v1.3 Self-Maintaining Public Docs` milestone (`docs-freshness` workstream). Over Phases 20 through 23, the Vox documentation platform established automated deployment recovery (Phase 20), responsive collapsible reader layouts (Phase 20.1), deterministic claim and mention extraction with prune classification (Phase 21), a code-anchored freshness ledger with baseline drift gating and PR impact comments (Phase 22), and contract-generated reference pages with automated crate API docs (Phase 23).

Phase 24 translates this deterministic verification machinery into reader- and agent-visible surfaces and equips project maintainers with the empirical evidence needed to decide the v1.4 milestone trajectory:

1. **Reader Trust Signals (TRUST-01)**: Every rendered documentation page displays an explicit trust banner reflecting its freshness state in `contracts/reports/docs-freshness/ledger.v1.json` (`Verified against <sha>`, `May be out of date — code changed since verification`, or `Unverified`). Navigation sidebar items for non-verified pages are tagged with status badges.
2. **Curated Agent Index (TRUST-02)**: The curated `.well-known/llms.txt` is strictly filtered to only contain verified, reader-facing pages. CI fails if any link in this curated set points to an unverified, drifting, or Internals page.
3. **Single-Source Agent Index (TRUST-03)**: The hand-maintained `docs/src/.well-known/llms-full.txt` is retired and replaced with an automated HTTP 301 redirect to `/llms-full.txt`, eliminating split-brain doc drift for AI agents.
4. **Visual Stepper Coverage (TRUST-04)**: Playwright visual-stepper tests in `docs-astro/tests/` verify trust banner and badge rendering across desktop, tablet, and mobile viewports in light and dark modes, archiving screenshots in `test-results/review-bundle/`.
5. **Hosted Bot & Academic Evaluation (EVAL-01)**: A comprehensive architecture research document evaluates hosted docs bots (Promptless, Dosu, Mintlify Agent, DeepDocs) and academic synchronization literature (DocPrism, CASCADE), establishes expected false-positive and acceptance baselines, and codifies the Decision D9 numeric pivot rule.
6. **Golden Drift Eval Set (EVAL-02)**: A machine-readable contract at `contracts/reports/docs-freshness/golden-drift-eval-set.v1.json` categorizes real historical drift incidents from Vox git history (`e2bb133a1`, `49a08f34e`, `f48dbc810`, `59e30f6b6`, `94822d35d`, etc.) to serve as an immutable benchmark for scoring both custom LLM claim verifiers and external tools.

## 1. Architecture & Data Model: Freshness Ledger Integration

### 1.1 Freshness Ledger Ground Truth (`ledger.v1.json`)

The state of documentation across the workspace is governed by `contracts/reports/docs-freshness/ledger.v1.json`, generated by `vox audit docs --update-ledger`.

#### Ledger Structure Analysis
- **Head Commit**: 40-character hexadecimal string representing the commit SHA at audit time (e.g. `"b64377d402f207a588f9c6b2e71ede6679340105"`).
- **Keying Scheme**: Pages are keyed by repository-relative paths:
  - Standard docs: `"docs/src/tutorials/tut-getting-started.md"`, `"docs/src/AGENTS.md"`.
  - Mounted repository docs: `"crates/vox-tauri-stt/README.md"`, `"README.md"`.
- **States**:
  - `verified`: All extracted anchors match verified symbol hashes, and `broken_mentions` is empty.
  - `drifting`: Anchors exist and were previously verified, but underlying code anchor hashes have changed in git history since `last_verified_commit`.
  - `broken`: Extracted claims or mentions cannot be resolved against the codebase or contracts.
  - `unanchored`: Page contains prose without detected code anchors or explicit claims; cannot be deterministically proven fresh.
  - `historical`: Marked with `status: archive` or `status: historical`.
- **Commit Format**: `last_verified_commit` is either `null` or a 40-character hexadecimal full SHA.

### 1.2 Route and Path Resolution in Docs-Astro

In `docs-astro`, documents are ingested from `docs/src/` and mounted repository paths. Starlight routes map directly to source files through the existing resolution algorithm in `docs-astro/src/routeData.ts`:

```typescript
let sourcePath: string | null = null;
if (entryData?.mounted_from && typeof entryData.mounted_from === 'string') {
  sourcePath = entryData.mounted_from;
} else {
  const cleanPath = route.entry.filePath.replace(/^src\/content\/docs\//, '');
  sourcePath = `docs/src/${cleanPath}`;
}
```

By querying `ledger.pages[sourcePath]`, any component or middleware can obtain:
1. `pageRecord.state` (`verified`, `drifting`, `broken`, `unanchored`, `historical`)
2. `pageRecord.last_verified_commit` (e.g. `b64377d...`)
3. `pageRecord.broken_mentions` (list of unresolved tokens)

## 2. Starlight 0.38 Component Integration (TRUST-01)

### 2.1 Page Banner Architecture

Starlight 0.38 natively includes a `Banner.astro` component located at `@astrojs/starlight/components/Banner.astro`, which renders content placed in `Astro.locals.starlightRoute.entry.data.banner`.

In `docs-astro`, `src/routeData.ts` sets `entryData.banner` for status policies (`research`, `roadmap`, `deprecated`, `legacy`) using `statusPolicy(status)` from `src/utils/page-status.mjs`.

To support TRUST-01 without conflicting with status banners, the system utilizes a two-tier banner component override registered in `docs-astro/astro.config.mjs`:

```javascript
// docs-astro/astro.config.mjs
starlight({
  // ...
  components: {
    Sidebar: './src/components/Sidebar.astro',
    TableOfContents: './src/components/TableOfContents.astro',
    PageSidebar: './src/components/PageSidebar.astro',
    Banner: './src/components/Banner.astro', // Custom Banner override
  },
})
```

#### Custom `Banner.astro` Implementation
The custom `Banner.astro` reads both `entry.data.banner` (status policy) and the page freshness record from `contracts/reports/docs-freshness/ledger.v1.json`:

```astro

const route = Astro.locals.starlightRoute;
const entry = route.entry;
const status = entry.data.status;
const sourcePath = route.entry.data._sourcePath;

<!-- Render standard Starlight status banner if present (research, roadmap, deprecated) -->

  <div class={`vox-trust-banner vox-trust-${freshness.state}`} data-pagefind-ignore>

      <span class="vox-trust-indicator" aria-hidden="true"></span>
      <span class="vox-trust-text">
        {freshness.state === 'verified' && (

            <strong>Verified:</strong> Accurate against commit{' '}
            <code>{freshness.shortCommit}</code>
          </>
        )}
        {freshness.state === 'drifting' && (
          <>
            <strong>May be out of date:</strong> Code changed since verification (at <code>{freshness.shortCommit}</code>).
          </>
        )}
        {(freshness.state === 'broken' || freshness.state === 'unanchored') && (
          <>
            <strong>Unverified:</strong> This page has not yet been anchored to automated code tests.
          </>
        )}
      </span>
      {freshness.state === 'verified' && freshness.commitUrl && (
        <a href={freshness.commitUrl} class="vox-trust-link" target="_blank" rel="noopener noreferrer">
          View Commit
        </a>
      )}
    </div>
  </div>
)}
```

### 2.3 Sidebar Badges for Non-Verified Pages

In `docs-astro/src/utils/sidebar.mjs`, `getSidebar()` builds navigation tree items using `makeItem(p)`. Currently, badges are attached based on frontmatter status (`STATUS_BADGE[p.status]`).

To satisfy TRUST-01 ("Sidebar badges mark non-verified pages"):
1. `sidebar.mjs` loads `contracts/reports/docs-freshness/ledger.v1.json` once at build time.
2. For each page in `mainPages` (excluding the `Internals` category, which already has its own section badge), the page's ledger state is checked.
3. If a page's status badge does not already take precedence, a freshness badge is attached:
   - `state === 'drifting'`: `badge: { text: 'Drifting', variant: 'caution' }`
   - `state === 'broken'` or `state === 'unanchored'`: `badge: { text: 'Unverified', variant: 'note' }`
   - `state === 'verified'`: No badge required (clean signal; absence of warning indicates standard reader trust).

## 3. Agent Surfaces & LLMs.txt Consolidation (TRUST-02, TRUST-03)

### 3.1 Retiring Split-Brain `llms-full.txt` (TRUST-03)

Currently, two versions of `llms-full.txt` exist in the repository:
1. `docs/src/.well-known/llms-full.txt`: Hand-committed Markdown/text file with outdated manual lists.
2. `docs-astro/dist/llms-full.txt`: Automatically generated by `starlight-llms-txt` plugin, containing concatenated documentation of all public pages while strictly excluding `Internals`.

#### Decommissioning Steps:
1. Delete `docs/src/.well-known/llms-full.txt` and `docs-astro/public/.well-known/llms-full.txt`.
2. Add a permanent redirect rule to `docs-astro/public/_redirects`:
   ```
   /.well-known/llms-full.txt   /llms-full.txt   301
   ```
3. Update `docs-astro/tests/build-output/llms.spec.ts` to assert that:
   - `dist/.well-known/llms-full.txt` is absent from disk.
   - `dist/llms-full.txt` exists and is generated.
   - `_redirects` contains the 301 mapping.

### 3.2 Curated `current` `llms.txt` Validation (TRUST-02)

`docs/src/.well-known/llms.txt` serves as the high-priority entry point for AI agents.

#### The Integrity Invariant:
CI must fail if any URL in `docs/src/.well-known/llms.txt`:
1. Points to an `Internals` page (policy: `status: research | roadmap` or categorized under Internals).
2. Points to a non-verified page (`state !== 'verified'` in `ledger.v1.json`).

#### Implementation in Playwright Build-Output Test (`llms.spec.ts`):
```typescript
test('curated .well-known/llms.txt links point only to verified reader-facing pages (TRUST-02)', () => {
  const llmsPath = join(REPO_ROOT, 'docs/src/.well-known/llms.txt');
  const content = readFileSync(llmsPath, 'utf8');
  const ledgerPath = join(REPO_ROOT, 'contracts/reports/docs-freshness/ledger.v1.json');
  const ledger = JSON.parse(readFileSync(ledgerPath, 'utf8'));

  const linkRegex = /\[([^\]]+)\]\((https:\/\/voxlang\.org\/[^)]+)\)/g;
  let match;
  const invalidLinks: string[] = [];

  while ((match = linkRegex.exec(content)) !== null) {
    const url = match[2];
    const pathSlug = url.replace('https://voxlang.org/', '').replace(/\/$/, '');
    
    // Resolve slug to source doc
    const pageEntry = Object.entries(ledger.pages).find(([sourcePath, data]: [string, any]) => {
      return sourcePath.includes(pathSlug);
    });

    if (!pageEntry) {
      invalidLinks.push(`${url} (not found in freshness ledger)`);
      continue;
    }

    const [sourcePath, pageData] = pageEntry as [string, any];
    if (pageData.category === 'Internals' || pageData.status === 'research' || pageData.status === 'roadmap') {
      invalidLinks.push(`${url} (points to Internals page)`);
    }

    if (pageData.state !== 'verified') {
      invalidLinks.push(`${url} (ledger state is '${pageData.state}', expected 'verified')`);
    }
  }

  expect(invalidLinks, `Invalid links in curated llms.txt: \n${invalidLinks.join('\n')}`).toEqual([]);
});
```

#### Alignment Strategy:
Currently, 28 pages in `ledger.v1.json` are in `state: verified`. Core pages listed in `llms.txt` that are currently unverified or drifting must either have their broken mentions resolved and re-attested via `vox audit docs --attest <path>`, or the curated `llms.txt` list must be pruned down strictly to the confirmed verified set (e.g. `AGENTS.md`, `contributor-hub.md`, `wire-format-v1-ssot.md`, `ref-type-system.md`).

## 5. Hosted Docs Bot & Academic Literature Benchmark (EVAL-01)

### 5.1 Industry Hosted Documentation Bots

| System | Primary Mode | Codebase Grounding | Reported / Observed PR Acceptance | False-Positive Flag Rate | Cost Profile | Suitability for Vox |
|---|---|---|---|---|---|---|
| **Promptless** (`promptless.ai`) | Merged PR triggers draft doc PR | Git diffs, PR comments, Doc Detective tests | 40%–60% on API reference; <25% on architectural docs | Moderate (20%–35%) on structured changes | $1,000–$1,500/mo (Growth) | Low (No `.vox` parser; calls third-party LLM directly) |
| **Dosu** (`dosu.dev`) | Continuous GitHub webhook triage & PR docs | Issue history, git diffs, PR discussions | ~50% on simple docstring/API fixes | High (35%–50%) on conceptual explanations | Custom / Tiered | Low (Violates LLM facade policy; no custom compiler check) |
| **Mintlify Agent** (`mintlify.com`) | "Modify and wait for review" (batched PRs) | Connected repo code changes | ~65% on OpenAPI/TypeScript endpoint tables | Low on schemas; High (>45%) on prose | $450/mo (Pro) | Low (Requires migrating doc site off Starlight; no `.vox` support) |
| **DeepDocs / Dependadocs** | Per-commit bot PRs | Local AST extraction + unconstrained LLM | <20% (frequently closed without merge) | Severe (>60% notification fatigue) | OSS / Token costs | Banned (Direct unconstrained bot PRs trigger developer fatigue) |

### 5.2 Academic Baselines

#### 1. DocPrism (Xu, Wahab, Holmes, Lemieux — UBC, 2024)
- **Problem**: Out-of-the-box LLM prompting for code-documentation inconsistency detection produces a catastrophic **90% to 98% false-positive rate** because models flag normal high-level omissions (incompleteness) as bugs (incorrectness).
- **Solution (LCEF)**: Local Categorization and External Filtering restricts the LLM to local code completion and feeds output to deterministic filters.
- **Result**: Reduced false positives from 98% to 14%, raising F1 score from 0.22 to 0.77.
- **Takeaway for Vox**: Any LLM-based documentation verifier must never be asked open-ended questions like "Is this doc accurate?". It must only verify specific extracted claims against exact AST symbol spans.

#### 2. CASCADE (Consistency Analysis for Source Code And Documentation through Execution — 2024/2025)
- **Problem**: Natural language documentation drifts silently from code behavior.
- **Solution**: Automated test synthesis from doc prose coupled with a strict dual-condition check: an inconsistency is reported *only* if the existing code fails the generated test while code generated from the documentation passes it.
- **Takeaway for Vox**: Corroborates Vox's TUT-02 and `vox doctest` approach: executable docs-as-tests provide 100% precision.

### 5.3 The Decision D9 Numeric Pivot Rule

Decision D9 in `REQUIREMENTS.md` establishes:
> "No hosted-bot trial. Instead, gather published accuracy and acceptance data for hosted docs bots and set a pivot rule: if they are far better than what we can build, switch to buying."

#### Quantitative Pivot Thresholds:
To justify pivoting away from building the in-house v1.4 LLM layer and buying a hosted solution, an external vendor must satisfy **ALL** of the following quantitative criteria:

1. **PR Acceptance Rate ($\ge 80\%$)**: Draft PRs opened by the vendor must achieve an acceptance rate of at least 80% without manual developer rewrites on the golden eval set.
2. **False Positive Rate ($\le 10\%$)**: Inconsistency detection must produce fewer than 10% false alarms on reader-facing current pages.
3. **Language & Compiler Native Execution**: The vendor must support compiling `.vox` source files, checking bare keywords (`table`, `query`, `mutation`, `server`, `tool`), and running `vox check` and `vox test` in their sandbox.
4. **Policy Compliance**: Must route LLM calls through local or private infrastructure without sending proprietary repository code to unauthorized third-party vendors, adhering to `AGENTS.md` and `contracts/secrets`.
5. **Cost Effectiveness**: Total cost must be less than $100/month (our planned in-house nightly verifier budget is $13–$45/month).

#### Pivot Determination:
**VERDICT: GO ON IN-HOUSE BUILD (NO-GO ON VENDOR PURCHASE).**
No commercial docs bot currently supports the Vox programming language, understands `.vox` grammar, or compiles doctests. Using a vendor bot would reintroduce hallucinated retired syntax (e.g. `@endpoint`) and corrupt code fences. Furthermore, the deterministic foundation constructed in v1.3 (symbol-span anchors, `command-registry`, `ledger.v1.json`) provides our in-house verifier with a grounding harness superior to any general-purpose SaaS bot.
