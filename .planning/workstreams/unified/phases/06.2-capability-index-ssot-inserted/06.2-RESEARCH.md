## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01:** The index is a **separate generated join file**, `contracts/capabilities/capability-index.v1.json`. It is built *from* the existing `contracts/capability/capability-registry.yaml` plus `contracts/gui/surface-registry.v1.yaml`, `docs/src/architecture/layers.toml`, docs frontmatter, the skills catalog, and the graph-coverage snapshot (D-07).
  - `capability-registry.yaml` stays transport-only and is **not** extended. Presentation and join data must not churn MCP/CLI codegen.
  - **Reversibility:** costly — 06.3–06.6 and llms.txt will all read this path and schema. Moving it later means touching every consumer.
- **D-02:** Each row has a `kind` discriminator. There is one row per capability (~1332), plus rows for **non-operation nodes**: crates, GUI surfaces, doc pages, and skills that back no operation. This lets the palette and atlas find a crate or doc that has no command. Cross-references are by id, not nesting.
- **D-03:** Consumers that read the index in this phase: `vox explain` / `vox features`; **generated `llms.txt` / `vox-docs.json` capability sections**; **a GUI build artifact** (TS/JSON emitted into the vox-gui build so 06.3/06.4/06.5 just import it); **an MCP tool**.
- **D-03a:** Implement `explain`/`features` as operations-catalog entries, so that each one generates both its CLI path and its MCP tool (e.g. `vox_capability_explain`) through the existing `vox ci operations-sync` chain. Do not hand-register an MCP tool.
- **D-04:** The owning crate is **derived, with a declared override**. The generator finds the crate that holds the CLI handler / MCP tool implementation (via the command registry and source paths). An optional `owner_crate` field in `contracts/operations/catalog.v1.yaml` overrides the derived value when it is wrong. The layer always comes from `layers.toml`, never from a second declaration.
- **D-05:** **Unresolved owners are ratcheted.** Record a count of capabilities with no resolvable owner. CI fails if the count rises; it may only fall. Reaching 0 is not required in this phase.
- **D-06:** **Doc links** come from two sources: every CLI/MCP capability defaults to its anchor in `docs/src/reference/cli-command-surface.generated.md` (or the MCP tool reference); any `docs/src/**` page may claim capability ids in a new frontmatter key, `capabilities: [<id>, …]`, for richer links. This new key must be accepted by the `vox-doc-pipeline` frontmatter lint.
- **D-07:** Coverage kinds (Surfaced / OrphanBackend / DeadEnd / CliOnly) come from a **separately committed snapshot**, `contracts/reports/graph-coverage.v1.json`. Nightly or an explicit `--refresh` updates it from `vox graph coverage`. The index generator **only joins** the snapshot. `vox ci ssot-drift` checks the deterministic join and **never builds the graph**.
- **D-08:** **Staleness is shown, not gated.** The index records the snapshot's source commit sha and date. `vox explain` and the GUI display "coverage as of `<sha>` (`<date>`)". Gating on coverage waits for 06.4 (DISC-10/11).
- **D-09:** `vox features` groups by a **new curated `domain` field**. Vocabulary is user-facing: compiler, orchestrator, mesh, ML/Mens, research, secrets, GUI, data, CI, and similar. It is derived from owner crate/layer by default, with an override in the catalog. The existing `product_lane` stays as a secondary facet. Define the vocabulary as a small committed list (not free text) so the drift gate can validate it.
- **D-10:** `vox explain <thing>` tries an **exact match first, then a fuzzy shortlist**. An exact match on capability id, CLI path, MCP name, surface `view_key`, crate name, or skill name prints the full card. Otherwise it prints a ranked shortlist. Use the existing `vox-search` lexical scoring if it is cheap to reach without a new crate edge; otherwise use simple local scoring. Semantic search stays deferred (DISC-v2-02).
- **D-11:** An explain card shows all four groups: **Equivalents** (CLI invocation, MCP tool name, GUI surface with a deep link, Catalog generic form); **Location** (owning crate, layer, source path, docs link); **Status** (coverage kind with snapshot age, catalog tier Recommended/Advanced/FeatureGated, side-effect class); **Related** (up to 5 siblings in the same domain or crate).
- **D-12:** Output is a **human-readable card by default, and `--json` emits the raw index row(s)**, following existing `vox` CLI conventions.

## Summary

The whole phase composes existing, well-trodden machinery; the only genuinely new code is a join + render step and a small shared resolver. `vox ci operations-sync` fans one catalog (`contracts/operations/catalog.v1.yaml`, 1298 ops) out to the MCP tool registry, CLI command registry and capability registry; adding an op with both `cli` and `mcp` projections produces both surfaces in generated YAML, **but the MCP tool still needs a hand-written dispatch arm and input-schema arm** (`verify_mcp_dispatch_coverage` and `verify_mcp_input_schema_coverage` fail without them). D-03a's "do not hand-register an MCP tool" is therefore true only for the registry rows, not the handler.

All needed edges already exist: `vox-cli -> vox-capability-registry` and `vox-orchestrator-mcp -> vox-capability-registry` are in `contracts/ci/crate-edges.allow.v1.json`, and `vox-cli` already depends on `vox-plugin-catalog`, `vox-graph-reader`, `vox-doc-pipeline`, `serde_yaml`, `toml`, `strsim`. The recommended split is: **schema + embedded loader + exact/fuzzy resolver + card renderer in `vox-capability-registry` (L2, no new workspace edges)**, and **the join/generate/verify step in `vox-cli` (L5) next to `gui_surface_registry.rs`**. No new crate edge is required, so nothing needs user authorization.

Three findings change the plan relative to CONTEXT.md and need planner attention: (1) the graph-coverage snapshot is thin and lossy: CLI graph node ids are `cli:<group>:<last-segment>` (197 of 910 nested CLI ops collide) and only 2 MCP tools exist as `tool:` nodes, so "coverage kind" will be `cli_only`/null for nearly everything, and that is honest rather than a bug; (2) the CLI-surface doc has no per-command anchors (single table), so D-06's "anchor" must be page-level; (3) `layers.toml` has **130** crates, not 151.

**Primary recommendation:** Add `vox ci capability-index [--write|--tighten|--refresh-coverage]` in `vox-cli` that writes four artifacts (index JSON, GUI TS, llms regions, vox-docs.json key) from one pure `build_index(inputs) -> CapabilityIndex` function; keep join + resolver logic pure and unit-tested; put `explain`/`features` as two paired catalog ops whose CLI handler and MCP handler both call `vox_capability_registry::explain::*` over the `include_str!`-embedded index.

### Pattern 1: Byte-exact write-or-verify (copy, do not reinvent)
**What:** One function writes (`--write`) or verifies (default) each artifact; text compared after LF normalization.
**Source:** [VERIFIED: crates/vox-cli/src/commands/ci/operations_catalog.rs:906-924]
```rust
fn write_or_verify_text(path: &Path, text: &str, write: bool, stale_hint: &str) -> Result<()> {
    if write {
        if let Some(parent) = path.parent() {
            fs::create_dir_all(parent)?;
        }
        fs::write(path, normalize_lf(text)).with_context(|| format!("write {}", path.display()))?;
        println!("wrote {}", path.display());
        return Ok(());
    }
    if !path.is_file() {
        return Err(anyhow!("missing {}; {stale_hint}", path.display()));
    }
    let existing = read_utf8_path_capped(path)?;
    if normalize_lf(&existing) != normalize_lf(text) {
        return Err(anyhow!("{} is stale; {stale_hint}", path.display()));
    }
    println!("OK {}", path.display());
    Ok(())
}
```
Make it `pub(crate)` (currently private `fn`) and reuse it for all four artifacts.

### Anti-Patterns to Avoid
- **Reading the compiled clap tree in the generator.** `build_catalog()` reflects `VoxCliRoot::command()`, which varies with cargo features; `gui_surface_registry.rs` already documents and avoids this (`top_level_groups` reads `command-registry.yaml` instead). Derive tier from the registry's `feature_gate` plus the `tier_for_path` rule (command_catalog.rs:399-413), not from a built catalog.
- **Timestamps or maps with nondeterministic order in the index.** Use `BTreeMap`/sorted `Vec`; `serde_json` is `preserve_order` workspace-wide so field order = declaration order.
- **Adding `owner_crate`/`domain` as non-skipping `Option` fields on `OperationRow`.** The catalog is re-serialized with every field incl. nulls (e.g. `description_human: null`); un-skipped new fields rewrite all 1298 rows. Use `#[serde(default, skip_serializing_if = "Option::is_none")]`, add both to the JSON Schema `operationRow.properties` (it has `additionalProperties: false`), and copy them in `apply_prev_planner_metadata` (operations_catalog.rs:384-401) so `--target catalog` rebuilds preserve them.
- **Running `vox graph` inside `ssot-drift`.** Forbidden by D-07.
- **Per-op `owner_crate` overrides for the long tail.** Use a group-level table in `domains.v1.yaml` (see Q3); per-op override stays available.

## Common Pitfalls

### Pitfall 1: Coverage kind is thin and lossy (see Q5)
**What goes wrong:** Planner/executor expects a coverage kind for ~1332 rows; only ~529 CLI rows (529/910 nested) and 2 MCP rows have a snapshot key, 197 CLI rows are ambiguous, and every CLI value today is `cli_only`.
**Why:** Graph node ids are `cli:<group>:<last>`; `tool:` nodes come from the GUI crate's dispatch-like tables.
**How to avoid:** Store `coverage` as `{kind|null, basis, ambiguous}`; make the DISC-01 test assert "kind or null with reason", never "non-null". Do not try to fix graph id scheme here (06.4 territory).
**Warning signs:** A test that counts non-null coverage rows against a magic number.

### Pitfall 2: Generator depends on build features
**What goes wrong:** Reading `command_catalog::build_catalog()` makes the committed index differ between a default build and the CI feature build; bot and local keep overwriting each other (the exact bug documented in `gui_surface_registry.rs` `top_level_groups`, commit 9ae16c97b).
**How to avoid:** Read `command-registry.yaml` + `feature_gate`; compute catalog tier with the same rule as `tier_for_path` (`FeatureGated` if gate present, `Recommended` for top-level `build|check|run|test|bundle|dev|doctor|completions`, else `Advanced`), by moving/duplicating that 15-line function as `pub(crate)` rather than building the clap tree.

### Pitfall 3: `OperationRow` new fields churn the catalog
See Anti-Patterns. Also: the JSON Schema has `additionalProperties: false` for `operationRow`, so the schema edit is mandatory, and `owner_crate` should be validated against `layers.toml`, `domain` against `domains.v1.yaml`, in the generator (clear errors) rather than via schema enums.

### Pitfall 4: `vox-gui` fresh-worktree prerequisites
Building/testing `vox-gui` (needed if the planner touches the UI type-check) fails in a fresh worktree until the sidecar exists (`vox run scripts/gui-build.vox`) and `crates/vox-gui/ui/dist` exists (`pnpm install && pnpm build` in `crates/vox-gui/ui`) [CITED: AGENTS.md §Perennial Bug Patterns]. This phase should only need `tsc`/vitest on the new generated TS if at all; do not run `cargo build -p vox-gui` locally.

### Pitfall 5: Size and bundle weight of the index
Estimated from the live catalog (my script, placeholder values for non-catalog fields): 1335 rows ~685 KB pretty / ~540 KB minified; with the GUI-trimmed projection (drop `description`/`tags`) ~430 KB minified; real values with docs/owner/coverage fields will land around 0.5-0.8 MB. 923 of 1298 op descriptions are the boilerplate `CLI operation \`vox …\``, so description text adds little search value; `title` + path tokens carry the signal. **Recommendation:** committed JSON pretty-printed (reviewable even though `-diff`), GUI TS trimmed to `{id, kind, title, domain, cli, mcp, surface, crate, layer, docs, coverage}` plus a <=120-char description, emitted as a typed `const` array that 06.3 should code-split with a dynamic `import()`. [ASSUMED] gzip ratio; measure with `gzip -c` during implementation.

### Pitfall 6: Determinism and cross-platform
No timestamps in the index (snapshot metadata lives only in the snapshot and is copied verbatim). Sorted rows by `(kind order, id)`; `BTreeMap` for any map. Normalize all stored paths to `/` (`replace('\\', "/")`), never `canonicalize()` (Windows `\\?\` prefix; see the comment in graphify `Index`), strip `\r` from frontmatter input (`normalize_lf`), and rely on `.gitattributes` `text eol=lf`. Add the new files to `.gitattributes` next to lines 75-84 (`linguist-generated=true -diff`): `contracts/capabilities/capability-index.v1.json`, `contracts/reports/graph-coverage.v1.json`, `crates/vox-gui/ui/src/generated/capabilityIndex.generated.ts`. (The `-diff` attribute makes local `git diff` print "Binary files differ"; mutation proofs must compare file contents, not `git diff`.) The two `.well-known` files and `vox-docs.json` are hand-reviewed and should NOT be marked generated.

### Pitfall 7: Embedded index chicken-and-egg
First commit must contain a valid placeholder (`{"schema_version":1,"rows":[]}` that satisfies the schema) before `index.rs` uses `include_str!`. A schema-valid but empty index must not make `explain` panic (return "no match"). Sequence tasks: types+placeholder -> generator -> real `--write` -> wire `explain`.

### Pitfall 8: New top-level commands mutate unrelated generated files
`vox ci gui-surface-registry --write` appends `none`-tier rows for `explain` and `features` to `contracts/gui/surface-registry.v1.yaml` (112 -> 114 entries; `none` 80 -> 82) and rewrites TS/report; tests or docs that pin those numbers (e.g. CONTEXT's "112 entries, 80 none") will move. `gui-surface-coverage.v1.json` and the clap-path baseline also change. Run regenerators in dependency order (`operations-sync`, `command-sync`, `capability-sync`, `gui-surface-coverage`, `gui-surface-registry`, then `capability-index`) and commit them together (the history is full of "regenerate after merge" fixes; AGENTS.md says fix at the source).

### Pitfall 9: Surface/handler owner labels vs domain (see Q3 caveat)
Do not derive `domain` from `owner_crate` when the owner is `vox-cli`, `vox-cli-ci`, `vox-orchestrator-mcp`, or `vox-gui`.

### Pitfall 10: Frontmatter `---` detection
`lint_frontmatter` finds the closing delimiter with `after_dash.find("---")`; a `---` inside a value truncates the YAML. Your parser should split on a line that is exactly `---`. Duplicate/legacy frontmatter blocks exist (the lint has a `DuplicateFrontmatter` rule); on unparsable frontmatter, skip the page for `capabilities:` purposes and continue (never fail the generator on someone else's malformed page; the doc lint owns that).

### Pitfall 11: Doc-page churn from index membership
Keep `doc` rows opt-in (claimed or pinned). A full-docs index would drift on every new page and the fast-tier `ssot-drift` would block docs authors.

### Mutation proofs for the drift gate (required by AGENTS.md §PR & Review Discipline)
Guard each with a before/after presence check (`grep -c`) because a concurrent `fmt`/agent can revert the edit and give a meaningless pass:

2. **Source drift:** add a catalog op (or a surface-registry entry) without regenerating -> check mode fails; this is success criterion 2.
3. **Dispatch registration:** delete the `ds!("capability_index", …)` line -> the source-text test fails; restore.
4. **Ratchet:** introduce an op that resolves to no owner (unknown group) -> fails; raise the baseline by hand -> `--tighten` refuses / reviewer sees baseline change.
5. **MCP wiring:** remove the dispatch arm -> `capability_tool_dispatch` and `operations-verify` fail (precedent: commit 6e9b79286 body, "removing the dispatch arm fails history_tool_dispatch").
