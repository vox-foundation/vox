**Gathered:** 2026-10-08

<domain>
## Phase Boundary

Deliver one **generated, joined capability index** that answers "what can Vox do, where does it live, and how do I reach it". It covers CLI, MCP, GUI surfaces, docs, crates/layers, skills, and graph coverage. Its consumers are:

- `vox explain <thing>` and `vox features [--domain <d>]` (CLI, plus their MCP twin)
- generated `llms.txt` / `vox-docs.json` capability sections
- a GUI build artifact that phases 06.3–06.5 import

Requirements: DISC-01, DISC-02, DISC-03, DISC-04.

These belong to later phases and are out of scope here: palette UI (06.3), Explorer surface and the coverage *gate* (06.4), Atlas (06.5), journeys (06.6).

</domain>

<decisions>
## Implementation Decisions

### Index home & shape
- **D-01:** The index is a **separate generated join file**, `contracts/capabilities/capability-index.v1.json`. It is built *from* the existing `contracts/capability/capability-registry.yaml` plus `contracts/gui/surface-registry.v1.yaml`, `docs/src/architecture/layers.toml`, docs frontmatter, the skills catalog, and the graph-coverage snapshot (D-07).
  - `capability-registry.yaml` stays transport-only and is **not** extended. Presentation and join data must not churn MCP/CLI codegen.
  - **Reversibility:** costly — 06.3–06.6 and llms.txt will all read this path and schema. Moving it later means touching every consumer.
- **D-02:** Each row has a `kind` discriminator. There is one row per capability (~1332), plus rows for **non-operation nodes**: crates, GUI surfaces, doc pages, and skills that back no operation. This lets the palette and atlas find a crate or doc that has no command. Cross-references are by id, not nesting.
- **D-03:** Consumers that read the index in this phase:
  - `vox explain` / `vox features`
  - **generated `llms.txt` / `vox-docs.json` capability sections**
  - **a GUI build artifact** (TS/JSON emitted into the vox-gui build so 06.3/06.4/06.5 just import it)
  - **an MCP tool**
- **D-03a:** Implement `explain`/`features` as operations-catalog entries, so that each one generates both its CLI path and its MCP tool (e.g. `vox_capability_explain`) through the existing `vox ci operations-sync` chain. Do not hand-register an MCP tool.

### Crate ownership
- **D-04:** The owning crate is **derived, with a declared override**.
  - The generator finds the crate that holds the CLI handler / MCP tool implementation (via the command registry and source paths).
  - An optional `owner_crate` field in `contracts/operations/catalog.v1.yaml` overrides the derived value when it is wrong.
  - The layer always comes from `layers.toml`, never from a second declaration.
- **D-05:** **Unresolved owners are ratcheted.** Record a count of capabilities with no resolvable owner. CI fails if the count rises; it may only fall. Reaching 0 is not required in this phase.
- **D-06:** **Doc links** come from two sources:
  - Every CLI/MCP capability defaults to its anchor in `docs/src/reference/cli-command-surface.generated.md` (or the MCP tool reference).
  - Any `docs/src/**` page may claim capability ids in a new frontmatter key, `capabilities: [<id>, …]`, for richer links.
  - This new key must be accepted by the `vox-doc-pipeline` frontmatter lint.

### Graph coverage
- **D-07:** Coverage kinds (Surfaced / OrphanBackend / DeadEnd / CliOnly) come from a **separately committed snapshot**, `contracts/reports/graph-coverage.v1.json`. Nightly or an explicit `--refresh` updates it from `vox graph coverage`.
  - The index generator **only joins** the snapshot.
  - `vox ci ssot-drift` checks the deterministic join and **never builds the graph**.
- **D-08:** **Staleness is shown, not gated.** The index records the snapshot's source commit sha and date. `vox explain` and the GUI display "coverage as of `<sha>` (`<date>`)". Gating on coverage waits for 06.4 (DISC-10/11).

### explain / features UX
- **D-09:** `vox features` groups by a **new curated `domain` field**.
  - Vocabulary is user-facing: compiler, orchestrator, mesh, ML/Mens, research, secrets, GUI, data, CI, and similar.
  - It is derived from owner crate/layer by default, with an override in the catalog.
  - The existing `product_lane` (interop/ai/platform/data/app/workflow) stays as a secondary facet.
  - Define the vocabulary as a small committed list (not free text) so the drift gate can validate it.
- **D-10:** `vox explain <thing>` tries an **exact match first, then a fuzzy shortlist**.
  - An exact match on capability id, CLI path, MCP name, surface `view_key`, crate name, or skill name prints the full card.
  - Otherwise it prints a ranked shortlist of fuzzy candidates to choose from.
  - Use the existing `vox-search` lexical scoring if it is cheap to reach without a new crate edge; otherwise use simple local scoring. Semantic search stays deferred (DISC-v2-02).
- **D-11:** An explain card shows all four groups:
  - **Equivalents:** CLI invocation, MCP tool name, GUI surface with a deep link, and the Catalog generic form.
  - **Location:** owning crate, layer, source path, docs link.
  - **Status:** coverage kind with snapshot age, catalog tier (Recommended/Advanced/FeatureGated), side-effect class.
  - **Related:** up to 5 siblings in the same domain or crate.
- **D-12:** Output is a **human-readable card by default, and `--json` emits the raw index row(s)**, following existing `vox` CLI conventions.

### Claude's Discretion
- The index schema's field names and JSON Schema file. Follow the style of `contracts/capability/capability-registry.schema.json`.
- Which crate hosts the generator and loader:
  - The natural home is extending `crates/vox-capability-registry` (L2).
  - The generator subcommand sits next to `operations_catalog.rs` / `gui_surface_registry.rs` under `crates/vox-cli/src/commands/ci/`.
  - **New crate edges must not be self-authorized.** If one is needed, propose it in the PR (AGENTS.md §Dependency Discipline).
- The exact derivation heuristic for owner crates, and the initial domain vocabulary list.
- The format of the GUI artifact (full JSON vs a trimmed TS module). Keep it small enough for the GUI bundle.
- How `llms.txt` keeps its hand-written preamble while the capability sections are generated, e.g. marked generated regions.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `vox ci operations-sync`: already fans one catalog out to the CLI registry, MCP registry and capability registry. Adding `explain`/`features` ops yields both their CLI and MCP surfaces for free (D-03a).
- `vox-capability-registry` loader: a typed in-memory registry that the new index loader can extend.
- `vox ci gui-surface-registry --write`: an established pattern for emitting generated TS into `crates/vox-gui/ui/src/generated/` (template for the D-03 GUI artifact).
- `crates/vox-cli/src/command_catalog.rs`: `CatalogTier` (Recommended / Advanced / FeatureGated) feeds the card's Status section.
- `vox-graph-reader` coverage classification: the source for the D-07 snapshot.

### Established Patterns
- Contracts are YAML SSOT, generate JSON/TS outputs, and are verified by `ssot-drift` with `--write` regeneration. PR CI's `ssot-autoregen` bot commits drift, so never hand-regenerate after a merge.
- Generated artifacts are marked `linguist-generated` in `.gitattributes`. Add the new index and snapshot there.
- Ratchet baselines live under `contracts/` (e.g. crate-edges, fan-in snapshot). The D-05 unresolved-owner count follows the same "tighten only" rule.

### Integration Points
- `run_ssot_drift` in `crates/vox-cli/src/commands/ci/run_body_helpers/docs.rs`.
- `vox-doc-pipeline` frontmatter lint (the new `capabilities:` key).
- The vox-gui build (`crates/vox-gui/ui/src/generated/`).
- `docs/src/.well-known/` generation.
