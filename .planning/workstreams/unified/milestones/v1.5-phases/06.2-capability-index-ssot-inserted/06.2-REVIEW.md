# Phase 06.2: Code Review Report

**Reviewed:** 2026-10-09
**Depth:** standard
**Files Reviewed:** 42
**Status:** issues_found

## Summary

Reviewed the capability-index generator (`vox ci capability-index`), the L2 resolve/render crate, the `vox explain` / `vox features` CLI, the MCP twins, and the llms.txt / vox-docs.json / TS emitters. Items checked and found sound:

- **Check mode is read-only.** `run(root, false)` only reads and compares, via `write_or_verify_text` with LF normalisation. It never opens the code graph. Only `--refresh-coverage` and `--tighten` write.
- **No path traversal.** The docs walk prunes `docs/src/archive`, does not follow symlinks, and claim ids are only compared with row ids.
- **Splice and escaping are safe.** `splice_region` fails closed on missing, duplicated or reversed markers. TS strings go through `serde_json::to_string`.
- **Line endings are pinned.** `.gitattributes` forces `eol=lf` on the `.well-known` files.
- **No new workspace crate edges.** The only manifest change is `strsim` on `vox-capability-registry`.
- **`preserve_order` is unified via `workspace-hack`.**
- **Tie-breaks are deterministic.** Candidates sort by `total_cmp` score, then id.

No critical issues. The warnings are one drift-determinism hazard, one silent-data-loss path in the docs-claims feature, one injection-hardening gap, two bounds/validation gaps, and two user-visible output defects.

## Warnings

### WR-01: "Related" group is crowded out by unrelated same-owner rows

**File:** `crates/vox-capability-registry/src/card.rs:190-208`
**Issue:** The Related filter is `same domain || same owner crate`. The rows are then sorted by id and truncated to 5. Most CLI rows are owned by `vox-cli`, and every MCP row by `vox-orchestrator-mcp`. These are the "surface crates" that `owner.rs` already knows say nothing about a domain (`SURFACE_CRATES`).

Verified against the committed `capability-index.v1.json`: `cli.check` (domain `compiler`) matches 515 candidate rows. Its Related list is the alphabetically first five: `cli.add` (deploy), `cli.architect` (ci), `cli.ars` (skills), `cli.ars.ludus`, `cli.ars.ludus.arena-join`. Same-domain siblings such as `cli.build` and `cli.compile` are cut. The unit tests use a tiny fixture where every owner is distinct, so the defect is invisible there.

**Fix:** Rank same-domain rows first, and ignore owner equality for surface crates.
```rust
const SURFACE_CRATES: [&str; 4] = ["vox-cli", "vox-cli-ci", "vox-orchestrator-mcp", "vox-gui"];
let same_owner = |r: &IndexRow| {
    row.owner.as_ref().zip(r.owner.as_ref()).is_some_and(|(a, b)| {
        a.crate_name == b.crate_name && !SURFACE_CRATES.contains(&a.crate_name.as_str())
    })
};
// ...and sort by (domain_mismatch, id) before `take(RELATED_LIMIT)`.
```
Add a test whose fixture has two rows sharing a surface-crate owner in different domains. Better, export the surface-crate list from one place; `owner.rs:24` has it today.

### WR-02: Index "skills" input comes from the compiled-in plugin catalog, so regeneration can be stale or non-reproducible

**File:** `crates/vox-cli/src/commands/ci/capability_index/inputs.rs:176-200` (with `scripts/ssot-regen.vox:30-36`)
**Issue:** `inputs.rs` states "Reads only checked-in contracts", but `load_skills()` calls `vox_plugin_catalog::all_plugins()` and `all_skill_bundles()`. Those are `include_str!("../catalog.toml")` baked into the running `vox` binary (`vox-plugin-catalog/src/lib.rs:13`).

`ssot-regen.vox` runs `plugin-catalog-sync --write` (step d), which rewrites `catalog.toml`. It then runs `capability-index --write` (step m) with the same, already-built binary. After any plugin-manifest change, one regen pass therefore writes `skill.*` rows from the OLD catalog. The `ssot-drift` gate, run with a freshly built binary, then reports the index stale. This is the pattern the repo's autoregen job is meant to avoid.

The same applies to any developer running an installed `vox` older than the checkout. The result depends on how the binary was built, not on committed inputs, which defeats the "check mode is deterministic from committed files" design goal.

**Fix:** Parse `crates/vox-plugin-catalog/catalog.toml` from `repo_root` (the crate already has a parser; expose a `parse(&str)`), or at minimum move `capability-index` after a rebuild step. Add a test that mutates a temp-dir copy of the catalog and asserts the skill rows change.

### WR-03: Malformed or unreadable docs frontmatter silently drops claims, and the doc lint does not catch it as documented

**File:** `crates/vox-cli/src/commands/ci/capability_index/docs_claims.rs:39-42`, `inputs.rs:125-137`, `crates/vox-doc-pipeline/src/pipeline/lint.rs:361-432`
**Issue:** `parse_meta` returns `None` on any YAML or type error. Examples: `capabilities: cli.foo` as a scalar, `title: 2026`, or a BOM before `---`. `load_doc_pages` also `continue`s on a read error, including a file over the size cap. The page then silently contributes no claim, and the index drifts without any error.

`documentation-governance.md` ("Malformed frontmatter is skipped by the index generator; the doc lint reports that error") and the module doc (Pitfall 10) rely on the lint owning that error. It does not. `lint_frontmatter` is a line-prefix scanner. It never parses YAML and has no `capabilities` handling. The two new lint tests (`capabilities_key_is_accepted`, `capabilities_block_list_is_accepted`) pass on the unmodified lint, because it never rejected unknown keys, so they prove nothing.

Net effect: an author who writes `capabilities: cli.secrets` loses the claim with no diagnostic anywhere. Also, `lint_frontmatter` ends the block at the first `---` anywhere in the text, while `split_frontmatter` requires an exact `---` line. These two parsers disagree.

**Fix:** Either make the generator fail on a page whose raw frontmatter contains a `capabilities:` line but fails to parse into `PageMeta`, or add a real lint rule for it. At minimum, make the generator error when it skips a page that mentions `capabilities`. Replace the two vacuous lint tests with one that fails when the rule is removed.

### WR-04: `single_line` / `safe_line` strip only Cc controls, leaving bidi, zero-width and Unicode tag characters in llms.txt

**File:** `crates/vox-cli/src/commands/ci/capability_index/join.rs:25-32`, `emit.rs:50-57`
**Issue:** The filter is `!c.is_control() || c.is_whitespace()`. `char::is_control` covers only category Cc. Category Cf survives. That includes U+202A..202E and U+2066..2069 (bidi overrides), U+200B..200D, U+2060, U+FEFF, and U+E0000..E007F (invisible "tag" characters).

`llms.txt` / `llms-full.txt` exist specifically for LLM consumption. They are fed from catalog descriptions and titles, and from doc-page frontmatter on the summary/title path. Invisible tag characters are the standard hidden prompt-injection carrier. The `<!--` guard (a good test) addresses visible markup only. The stated goal was "markup/control-char injection into llms.txt".

**Fix:**
```rust
.filter(|c| c.is_whitespace()
    || !(c.is_control()
        || matches!(*c as u32, 0x200B..=0x200F | 0x202A..=0x202E | 0x2060..=0x2064
                              | 0x2066..=0x2069 | 0xFEFF | 0xE0000..=0xE007F)))
```
Add a test with `\u{202E}` and `\u{E0041}` inputs.

### WR-05: Advertised input bounds are not enforced, and the length check runs after a full-input lowercase

**File:** `crates/vox-capability-registry/src/explain.rs:119-126`, `181-189`; `crates/vox-orchestrator-mcp/src/input_schemas.rs` (new arms); `capability_tools.rs:59-75`
**Issue:**
1. `resolve` does `query.trim().to_lowercase()` on the whole input before checking `MAX_QUERY_CHARS`. A multi-MB query is allocated and lowercased before rejection. The length is also measured on the lowercased text. `to_lowercase` can expand characters (U+0130 `İ` becomes 2 chars), so a 200-char query that satisfies the advertised `maxLength: 256` can be rejected as "too long (max 256 characters)".
2. `vox_capability_features.domain` advertises `maxLength: 64`, but the server never validates input against `tool_input_schema` (schemas are only advertised; `registry.rs` and `tool_search.rs` just expose them). `rows_in_domain` lowercases the full string and reflects it verbatim in `unknown domain \`{domain}\``, so the response size is unbounded.

**Fix:** Check `query.chars().take(MAX_QUERY_CHARS + 1).count() > MAX_QUERY_CHARS` on the raw trimmed input before lowercasing. Add a `MAX_DOMAIN_CHARS = 64` check in `rows_in_domain`, truncate the echoed value in the error, and add tests for both.

### WR-06: Hard-coded domain ids and duplicate vocabulary entries are never validated

**File:** `crates/vox-cli/src/commands/ci/capability_index/nodes.rs:129-136, 195`, `owner.rs:134-167`
**Issue:** `validate_domains` checks table values and the `platform` fallback only. `surface_row` falls back to the literal `"gui"`, `skills` rows use `"skills"`, and `doc_row` uses `"docs"`, none of them checked against `domains`. Removing or renaming one of those ids in `domains.v1.yaml` makes the generator emit rows whose domain is outside the vocabulary. `domain_counts` and `rows_in_domain` then never surface them, and `vox features --domain skills` becomes an "unknown domain" error. The schema does not catch it either (`domain` is a free nullable string).

Duplicate `domains[].id` entries are also accepted. `domain_counts` would then print duplicate lines.

**Fix:** In `validate_domains`, require `gui`, `skills`, `docs` and `platform`, and reject duplicate ids. Move the four constants to one place (`FALLBACK_DOMAIN` is already defined separately in `nodes.rs:21` and `owner.rs:22`).

### WR-07: `vox features --domain skills|docs` (text) prints nothing while `--json` lists the rows

**File:** `crates/vox-capability-registry/src/card.rs:264-323`
**Issue:** `render_features` renders only cli/mcp operations, a "Surfaces" section and a "Crates" section. Skill and Doc rows, which live in domains `skills` and `docs`, are never rendered. `vox features --domain docs` prints the heading and a lone `—`, although the rows exist and `--json` and the MCP `data` return them. The text view and the machine view disagree, and the `meta.text` of the MCP twin is empty-looking for those domains. `domain_counts` has no skill or doc column either.

**Fix:** Add `Skills` and `Docs` sections (via the existing `section` closure), or document that those domains are JSON-only. Add a test for `render_features(&idx, Some("skills"))`.

## Info

### IN-01: Duplicated dispatch logic, and partial writes on a late failure

**File:** `crates/vox-cli/src/commands/ci/providers.rs:116-133`, `run_body.rs:118-131`, `capability_index/mod.rs:65-94`
**Issue:** The `refresh_coverage` / `tighten` / `run` sequencing is implemented twice, once as an `and_then` chain and once imperatively. Separately, in `--write` mode `run` writes the index first, then llms regions, then vox-docs.json and the TS file. A missing marker in `llms-full.txt` therefore fails after the index has already been rewritten, leaving a half-regenerated tree.
**Fix:** Put the sequencing in one function in `capability_index`, e.g. `pub fn run_cmd(root, write, tighten, refresh)`. Compute and verify every artifact text up front, then write.

### IN-02: Two copies of the `RowKind` to string mapping

**File:** `crates/vox-capability-registry/src/card.rs:21-30`, `emit.rs:215-224`
**Issue:** The same six-arm match exists twice, beside the serde `snake_case` rename. A new kind needs three edits that compile fine if one is missed.
**Fix:** Add `RowKind::as_str()` in `index.rs` and use it in both places.

### IN-03: `description_human: Some("")` suppresses the fallback description

**File:** `crates/vox-cli/src/commands/ci/capability_index/join.rs:40`
**Issue:** `op.description_human.as_deref().unwrap_or(&op.description)` selects the empty string, `single_line("")` returns `None`, and the row gets no summary even though `description` is populated.
**Fix:** `.filter(|s| !s.trim().is_empty()).unwrap_or(&op.description)`.

### IN-04: The owner-ratchet baseline can be reset by deleting the file and running `--tighten`

**File:** `crates/vox-cli/src/commands/ci/capability_index/mod.rs:117-126`, `ratchet.rs:80-82`
**Issue:** `tighten(live, None)` bootstraps the baseline from the current unresolved set. Deleting `owner-ratchet.v1.json` and running `--tighten` therefore admits any newly ownerless command. It appears as a visible diff, but it contradicts "removal-only", and `run` itself treats a missing baseline as an error.
**Fix:** Gate bootstrap behind an explicit flag, or refuse when `git ls-files` already tracks the baseline.
