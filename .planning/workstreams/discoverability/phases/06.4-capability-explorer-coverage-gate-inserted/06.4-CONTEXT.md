<domain>
## Phase Boundary

Give users one place to **browse everything Vox can do by domain**, and give CI a gate that keeps **every capability group reachable or explicitly exempted**.

- **DISC-08:** a top-level Capability Explorer surface grouped by domain, showing each capability's status (dedicated surface / generic form / CLI-only / MCP-only or orphan).
- **DISC-09:** the surface classifier credits the Catalog's generic forms as a `generic_form` tier, so coverage reflects what is actually reachable.
- **DISC-10:** CI fails when a CLI group has no GUI representation (dedicated or generic) and no exemption with owner + reason.
- **DISC-11:** every `vox graph coverage` orphan/dead-end node is dispositioned and the undispositioned count is 0 and ratcheted.

Out of scope here:
- Architecture Atlas (06.5), time-to-find journeys (06.6)
- widening graph ingest to all MCP tools
- contextual per-panel help (DISC-v2-01) and semantic search (DISC-v2-02)
- classifying the remaining ~900 unclassified `side_effect_class` verbs (06.3 ratchet continues separately)

</domain>

<decisions>
## Implementation Decisions

### What "reachable" means (DISC-09, DISC-10)
- **D-01:** The **gate unit is the top-level CLI group** (88 groups today; 82 are tier `none` in `contracts/gui/surface-registry.v1.yaml`). Per-op gating is rejected: it would need ~1000 exemptions.
- **D-02:** The **`generic_form` tier is derived, not declared.** A group is `generic_form` automatically when its verbs are compiled into the GUI build and reachable through the Catalog form (the index row's `catalog_form`). A group whose verbs are feature-gated and not compiled in stays `none`. No hand-set `generic_form` values in the YAML (the `RepresentationTier::GenericForm` enum arm already exists in `gui_surface_registry.rs`).
  - **Reversibility:** costly — the tier semantics feed the registry, generated TS and the Explorer.
- **D-03:** The Explorer badges are exactly four: **Dedicated surface** (`live_backend` or `curated_decorator`), **Generic form**, **CLI-only** (not reachable in the GUI: not compiled in, or exempted), **MCP-only / orphan** (a backend capability with no CLI or GUI path).

### Orphan / DeadEnd disposition (DISC-11)
- **D-04:** **Exclude the `surface` node kind** from the orphan metric, with the reason recorded in the generator and docs. A `surface:` node has no callers by design (it is a UI entry point), so `orphan_backend` there is a classifier artifact: today all 32 surface nodes are flagged only for that reason. Disposition applies to backend kinds only (`cmd`, `tool`, `cli-command`).
  - Do not change `vox-graph-reader`'s classification semantics for this; apply the exclusion where the snapshot is consumed or generated.
- **D-05:** **Scope is the nodes the graph flags, in the kinds it covers.** Today that is 2 MCP tool nodes: `tool:vox_mesh_nodes` (`dead_end`) and `tool:vox_populi::inference_PROFILE` (`orphan_backend`, a templated placeholder-looking name). Do not widen the graph ingest to all ~342 MCP tools in this phase.
- **D-06:** **No exemptions for orphans or dead-ends: fix or delete.** Every flagged backend node must be surfaced or deleted. If the node is a stale artifact of the graph ingest (bad edge, placeholder), repair the ingest/source so it is not emitted; if it is real dead code, delete it. If it is a real tool with no GUI path and cheap to wire, surface it. The default when it cannot be surfaced cheaply is **delete/repair the source**.
  - This **amends DISC-11's wording** ("exempted with reason") — update REQUIREMENTS.md accordingly when planning. The exemption mechanism of D-10 applies to DISC-10 group gaps only, not to orphans.
- **D-07:** The orphan check is **a ratchet at zero**: the undispositioned flagged count in the committed coverage snapshot must be 0 and may never rise. It follows the 06.2/06.3 ratchet pattern (`capability_index/ratchet.rs`: baseline written only by explicit `--tighten`, never by `--write`).

### Explorer surface (DISC-08)
- **D-08:** A **new top-level surface** (`explorer`) in the `system` nav group, replacing the hidden Settings → Coverage table. The old `coverage` view_key redirects to it. Register it in `contracts/gui/surface-registry.v1.yaml`, `lib/navigation.ts` and `App.tsx` view routing, following the way existing surfaces register.
- **D-09:** **Domain → group → verb tree.** Left: domains (from `CAPABILITY_DOMAINS`) with counts and status mix. Main: top-level CLI groups for the selected domain as rows/cards with badges, expandable to their verbs. Filters: status, a search box, and a show-exempt toggle.
- **D-10a (actions):** each row offers: open the dedicated surface or the prefilled Catalog form (reuse the 06.3 `decideCliActivation`/prefill logic), the explain card (reuse `ExplainDrawer`), a docs link and a crate/layer link (the crate link becomes an Atlas link in 06.5), and the exemption reason (owner + reason + review date) where exempt.
- **D-11:** **Data: reuse the lazy-loaded capability index** (`useCapabilityIndex`) plus new group-level coverage and exemption fields emitted by the generator. In the same `generate_ts` change, **close the three TS explain-card parity gaps** left by 06.3 (docs `origin`, coverage `reason`, `ambiguous` flag).
- **D-12:** The 06.3 D-08a deferral lands here: the palette's capped-facet **"show more" hint becomes a link to the Explorer**.

### Gate scope & CI wiring (DISC-10)
- **D-13:** **The gate extends `vox ci gui-surface-registry`** (it already classifies top-level groups and fails on unclassified ones, and runs in `ssot-drift`). No new subcommand and no new catalog op.
- **D-14:** **Exemptions live in a new YAML contract**, `contracts/gui/coverage-exemptions.v1.yaml`, with `group`, `owner`, `reason` and a **`review_by` date** per entry. The gate fails when an entry is past `review_by`, names an unknown group, or exempts a group that is now represented (stale). Exemption count has a ratchet: it may only fall.
- **D-15:** **Rollout: seed exemptions from today's gaps, then ratchet.** The first run lists every group that is `none` and not derivable as `generic_form`; each gets an owner and reason (many will be "feature-gated, not compiled into the GUI build", e.g. `extras-ludus`, `ars`, `coderabbit`). Initial gate state is green. After that, new groups must be classified.
- **D-16:** **Gate rules enforced in CI:**
  1. A **new top-level CLI group** must be classified or exempted. If it is compiled into the GUI build it derives as `generic_form` and passes without human action.
  2. A **floor ratchet on the dedicated-surface count** (dedicated groups may not fall): so "dedicated vs generic" is a guarantee, not only a badge. The baseline is raised only by an explicit `--tighten`.
  3. A **new verb in a represented group** passes automatically.
  4. A verb **not compiled into the GUI build** counts as CLI-only on the badge and does not fail the gate unless its whole group is uncompiled (then rule 1 applies).
- **D-17:** **MCP-only tools warn, do not fail.** CI output prints the MCP-only count (303 of 342 today) and lists newly appearing MCP-only tools as a warning; the Explorer shows them under the MCP-only badge. A ratchet on that count is deferred: it would freeze agent-tool authoring and needs widened graph ingest first.

### Research-driven decisions (2026-10-12, from 06.4-RESEARCH.md)
- **D-18:** **The gate universe is 90 groups**, as in `contracts/reports/gui-surface-registry.v1.json`, which includes the hand-listed `dei` groups `attention` and `safety`. It is not the index's 88. Also clean the registry YAML: drop the duplicate `repl` row and keep `ludus`/`oratio`/`schola`/`search` as view rows without misclaiming top-level groups.
- **D-19:** **One shared `in_gui_build(status, gate)` predicate.**
  - A row counts as compiled into the GUI build iff its feature gate is satisfied by vox-cli's **default** features (`keyring-store`, `script-execution` per `crates/vox-cli/Cargo.toml`).
  - Use the predicate for both `catalog_form` (fixing `nodes.rs:78`, which treats every gated row as uncompiled) and derived `generic_form`.
  - Two tests pin it: one to Cargo's `default` list, one to the clap `build_catalog()` set.
  - Expected result: 64 groups derive `generic_form` and 14 stay `none` (the exemption seed).
- **D-20:** **Re-key Gamify/Voice (user decision 2026-10-12).**
  - Add an optional `mcp_namespace` field to the surface registry (schema + generator + TS).
  - Re-key `cli_group` from `ludus`→`gamify` and `oratio`→`speech`, so those dedicated surfaces are credited to the real CLI groups.
  - Keep MCP op-namespace joins (`ludus` 10 tools, `oratio` 3, `schola` 1) working through `mcp_namespace`.
  - Dedicated groups become 12.
- **D-21:** **DISC-11 scope is the committed snapshot kinds only (user decision 2026-10-12).** The kinds are `tool` and `cli-command`; `surface` is excluded per D-04. The `command` kind (~100 orphans / 419 dead-ends, mostly CLI-join artifacts; 11 real `vox_skill_*` calls emitted as `cmd:`) is **deferred**.
- **D-22:** **Repair both flagged tool nodes at the ingest source** (D-06 "repair the source"). In `vox-graph-reader`'s `mcp_tool_nodes`:
  - Stop matching env-var keys like `vox_populi::inference_PROFILE` (from `crates/vox-gui/src/commands/user_config.rs:88`).
  - Create `tool:` nodes from `contracts/mcp/tool-registry.canonical.yaml`, but only for names the GUI actually references. This resolves `tool:vox_mesh_nodes`, a real tool whose dispatch is in `vox-orchestrator-mcp`, so the edge from `SettingsView.tsx:178` stops dangling. It does not widen the node set to all 342 tools.
  - Do NOT use a charset filter: the registered tool `vox_compiler::ast_inspect` contains `::`.
  - Do not edit the GUI call sites, which would only hide the signal.
  - This is an ingest fix and does not change the `CoverageStatus` semantics, so it stays compatible with D-04.
  - After the repair, refresh the snapshot (`vox graph rebuild --corpus vox-gui-surface` → `vox ci capability-index --refresh-coverage --write`). Note in the docs that the orphan ratchet sees new orphans only after a refresh.
- **D-23:** **Gate code placement.**
  - The new check lives in `crates/vox-cli/src/commands/ci/gui_coverage_gate.rs`, called from `gui_surface_registry::run`. That file is 367 lines and the God-Object limit is 500.
  - The group rollup goes in a pure `capability_index/groups.rs` and is passed to `generate_ts`; `emit.rs` is already 708 lines.
  - Derived tiers are resolved at generation and never written back to the YAML. A hand-set `generic_form` is rejected (removed from the schema enum).
- **D-24:** **Review-date "today".** The `review_by` check uses the UTC wall clock, with an injectable date for tests and a `--today` flag; no env var. Past-due entries fail; entries due within 30 days warn. The HEAD commit date is not used, because it is useless on PR merge refs.
- **D-25:** **Ratchets.**
  - Reuse `RatchetSpec`. The exemption set (shrink-only) and the orphan set (zero) use it as is; the orphan spec's ctx carries the snapshot.
  - The dedicated floor adds a `Floor` direction over the SET of dedicated groups (12 after D-20), not a count.
  - Baselines: exemption and floor files under `contracts/gui/`, the orphan one under `contracts/capabilities/`.
  - `--tighten` is added to `vox ci gui-surface-registry` (`vox-cli-ci/src/cmd_enums.rs`, `run_body.rs`, `providers.rs`).
- **D-26:** **Surface-kind coverage rows** are mapped to null with a recorded reason at the consumption site, so the Explain card no longer shows `orphan_backend` for healthy surfaces.
- **D-27:** **MCP-only warning mechanics.** Always print the MCP-only count. In `--write` mode, warn on MCP-only names that are new relative to the previously committed index. No extra list file.
- **D-28:** **Explorer data and single-verb groups.**
  - Emit a `CAPABILITY_GROUPS` table (~90 entries) plus three row fields (`docOrigin`, `coverageReason`, `coverageAmbiguous`), keeping `ROWS_n` chunking and a uniform row shape (TS2590).
  - A group with only a bare-path row (43 of 88) renders as a childless row counted once.
- **D-29:** **Seeded exemptions need a human check.** The initial exemptions and their owner/reason wording go through a `checkpoint:human-verify` before commit. The ledger is user-authorized.

### Claude's Discretion

- Initial exemption owners/reasons wording and `review_by` horizon (suggest a date a few months out).
- How the two flagged tool nodes are investigated and resolved (D-06 default: repair/delete).

## Existing Code Insights

### Reusable Assets
- `gui_surface_registry.rs` already walks top-level CLI groups, classifies them, fails on unclassified groups and emits TS; the gate and derived tier extend it.
- The capability-index generator already joins surfaces, CLI rows, `catalog_form`, domains, tiers and the coverage snapshot; group rollups can be derived there.
- 06.2/06.3 ratchet machinery (`RatchetSpec` + `--tighten`-only baselines) is reusable for the new orphan ratchet, exemption-count ratchet and dedicated-count floor.
- 06.3's `ExplainDrawer`, `decideCliActivation`, prefilled Catalog form and `useCapabilityIndex` are the Explorer's row actions and data path.

### Established Patterns
- Contracts YAML → generator → committed JSON/TS, drift-checked by `vox ci ssot-drift`; `ssot-autoregen` regenerates drift on PRs. `gui-surface-registry --write` backfills `none`-tier rows for new top-level groups.
- Surfaces register in the surface-registry YAML, `navigation.ts` and `App.tsx`; a surface needs a Playwright spec with screenshots.
- Large generated TS must be chunked to typecheck (06.3 D-14).

### Integration Points
- `capability_index/emit.rs` (`generate_ts`) and `gui_surface_registry.rs` (tier derivation, gate).
- New `contracts/gui/coverage-exemptions.v1.yaml`, plus ratchet baselines under `contracts/`.
- `lib/navigation.ts`, `App.tsx`, `omnibarFacets.ts` (the "show more" link).

## Specific Ideas

- Today's baseline numbers for acceptance criteria: 88 CLI groups; 82 registry groups at `none`; ~400 of 998 CLI rows behind a cargo feature (`extras-ludus` 196, `ars` 132, `coderabbit` 30, `gui` 13, …); 303 of 342 MCP tools have no CLI twin; 32 + 2 graph-flagged nodes (32 are the surface-kind artifact).
- The derived `generic_form` tier will make most groups pass automatically; the gate's practical bite is on feature-gated groups and on the dedicated-count floor. Say this plainly in the gate's output and docs so it is not mistaken for a stricter check than it is.
