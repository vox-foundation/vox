<objective>
Measure whether Vox's compiler diagnostics help a model repair its code: pass@1 after k compiler-feedback turns, k = 1 and 3 (design §8, which ROADMAP Phase 12 lists among its design sections; reported with the same BENCH-03 statistics as every other metric).

Purpose: design §8 names this as a central claim of the language and a required secondary metric, and nothing measures it today. No REQUIREMENTS.md ID names it; this plan is tagged BENCH-03 because its output is a reported metric with bootstrap CIs and a resolution floor, and the planning return flags that a dedicated requirement ID would be cleaner.
Output: an opt-in repair loop in eval-corpus, per-sample repair trajectories, and per-turn statistics in the typed report.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| verifier diagnostics → model prompt | diagnostic text from `vox check`/`vox run` is sent back to the provider |
| model output → verifier | repaired candidates are executed like original ones |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-08-01 | Information disclosure | diagnostics sent to the provider | low | accept | the diagnostic is one line (max 200 chars) about the candidate itself; it can contain a temp-workdir path, which carries no secret |
| T-12-08-02 | Denial of service / cost | repair turns multiply requests | medium | mitigate | K is capped at 3, defaults to 0, repair cost counts toward `--max-spend-usd`, and spend-cap hits make the run incomplete |
| T-12-08-03 | Tampering | repaired results inflating pass@1 | medium | mitigate | the original AttemptOutcome is never replaced; repaired rates live in a separate field (tested) |
| T-12-08-04 | Elevation of privilege | executing repaired code | medium | accept | same verifier path and canary as original candidates (see T-12-02-05) |
</threat_model>
