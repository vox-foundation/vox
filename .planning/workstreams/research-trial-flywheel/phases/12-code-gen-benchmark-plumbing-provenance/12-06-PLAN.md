<objective>
Give every locally trained MENS adapter a training-lineage card and give eval a single check that refuses to label an adapter it cannot trace (BENCH-05; D-06, D-11).

Purpose: the local training arm writes no `AdapterCard` at all, the card type has no adapter or training-data hash, and `corpus_hash` is an xxh3 idempotency key, not the training data's identity. A `mens/*` score therefore cannot be traced to its training data. This plan adds the lineage fields, writes the card when a local run succeeds, and provides `check_for_eval`, which 12-07 calls from eval-corpus.
Output: lineage-bearing `AdapterCard`, a host-side card writer in `train_arm.rs`, a fingerprint wrapper in `vox-compiler`, and an eval-side card check in `vox-populi`.

Crate-edge note (verified 2026-10-11 against `contracts/ci/crate-edges.allow.v1.json`): vox-populi → vox-crypto exists, so hashing lives in vox-populi and both the writer (vox-ml-cli) and the eval gate (vox-cli → vox-populi exists) share one implementation. vox-ml-cli → vox-grammar-export and vox-populi → vox-grammar-export are absent, so the fingerprint goes through the existing vox-ml-cli → vox-compiler edge and is passed into vox-populi as a string. No new edge.
</objective>

## Recorded deviation (cloud training arm)

The cloud arm (`--cloud runpod|vast`, `card_from_manifest` in `pipeline_dispatch.rs`) already writes a card when its eval gate passes, but the bytes the pod trained on come from a Hugging Face dataset (`train_data_hf`) and are not observable host-side, so `train_data_sha256` and `training_manifest_digest` cannot be computed honestly there. This plan sets the cloud card's lineage fields to empty strings with a comment saying why. Those cards fail `validate_lineage`, so eval refuses to label cloud-trained rows (fail closed). Lifting this needs the pod to report the consumed file's hash (or the dataset file's LFS oid); that is surfaced to the user in the planning return, not silently dropped.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-06-01 | Spoofing | adapter swapped under a `mens/<run>` label | high | mitigate | `check_for_eval` re-hashes the adapter and compares to the card's `adapter_sha256`; mutation-proven by `swapped_adapter_is_refused` |
| T-12-06-02 | Tampering | card edited to match a swapped adapter | medium | accept | the card is a local file on the same trust domain as the trainer; the signed run bundle (12-09) binds the adapter hash eval actually observed, so a later swap is detectable from the bundle |
| T-12-06-03 | Repudiation | training data identity | medium | mitigate | `train_data_sha256` hashes the exact file path the trainer recorded as consumed, in the same process, right after success (RESEARCH pitfall 7) |
| T-12-06-04 | Information disclosure | card contents | low | mitigate | the card stores hashes, never training data contents; the path of the consumed file is kept only in `TrainingLineage` (in-memory), not as an identity field |
| T-12-06-05 | Tampering | legacy cards trusted by default | medium | mitigate | new fields default to empty and `validate_lineage` rejects empty, so pre-existing cards are refused, not trusted |
</threat_model>
