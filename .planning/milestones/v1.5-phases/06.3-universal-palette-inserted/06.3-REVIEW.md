# Phase 06.3: Code Review Report

**Reviewed:** 2026-10-10
**Depth:** standard
**Files Reviewed:** 33 (App.tsx, SettingsView.tsx, transport.ts, tauri.ts, surfaceComponents.tsx and gui-navigation.md were reviewed by phase diff only)
**Status:** issues_found

## Summary

The run-path decision (`decideCliActivation`) is sound. Enter can only run a compiled-in, leaf, no-required-arg verb whose class is exactly `read_only` or `none`, and unclassified and unknown classes fall to the form. The unit tests for it are good. The weak point is the backend confirm gate. It matches `cli.path` literally against argv tokens, but clap accepts aliases for several destructive paths, so the gate is bypassable without any trick beyond using a documented alias (CR-01). Separately, the gate is default-open: only 10 of ~1000 CLI rows are classified destructive, and obviously destructive verbs such as `db prune-apply` are not among them (WR-01). No test would catch deletion of the gate call in `execute_command` (WR-02).

The rest are real but lower-severity bugs: keyboard handling in the Omnibar (focused row ignored, IME Enter), a sticky index-load error, misleading facet totals, a stale-state race in the catalog form, and an unguarded keybind store.

Checked and found OK:
- Jaro-Winkler matches strsim 0.11, and the 0.25 length prune is mathematically exact.
- Rank tie-break is deterministic.
- Index and CLI text render only as React text, with no `dangerouslySetInnerHTML`.
- `ts_str` JSON-escapes every generated string.
- No new crate edges: `vox-cli` already depended on `vox-capability-registry`, and `vox-gui` on `vox-cli`.
- Lazy-import failure resets `pending`, so a later open does retry.

## Critical Issues

### CR-01: Destructive-op gate is bypassed by clap aliases (`models`, `orchestrator`, `graphify`/`search`)

**File:** `crates/vox-capability-registry/src/index.rs:150-164` (gate), `crates/vox-cli/src/lib.rs:538,572,212` (aliases)
**Issue:** `confirmation_required` compares whole non-flag argv tokens to `cli.path` segments, which come from the canonical clap names. The CLI declares aliases that clap resolves to the same command:
- `#[command(name = "model", visible_alias = "models")]` (lib.rs:572). The destructive row `cli.model.preferences.reset` has path `["model","preferences","reset"]`, so `execute_command(["models","preferences","reset"], …, confirmed=None)` returns `Ok(())` from `gate_execution` and the sidecar runs the reset.
- `Dei` has `visible_alias = "orchestrator"` (lib.rs:538). The destructive row `vox dei snapshot restore` is bypassed by `orchestrator snapshot restore`.
- The `graph` group has `alias = "graphify"` and `alias = "search"` (lib.rs:212). Any destructive `graph …` row added later is bypassable the same way.

This defeats the stated D-03/D-15 goal ("argv-bypass-resistant"). The tests only use canonical names, so nothing detects it. `Catalog` rows also expose `aliases` (`CommandCatalogForm` renders `cmd.aliases`), so the data to fix this exists.

**Fix:** Resolve argv through clap's own parser instead of string-matching the canonical names. Example in `vox-cli`:
```rust
pub fn canonical_path(argv: &[String]) -> Option<Vec<String>> {
    let mut cmd = VoxCliRoot::command(); // run on the big-stack worker, like build_catalog
    let mut matches = cmd
        .try_get_matches_from_mut(std::iter::once("vox".to_string()).chain(argv.iter().cloned()))
        .ok()?;
    let mut path = vec![];
    while let Some((name, sub)) = matches.remove_subcommand() {
        path.push(name); // clap returns the canonical name, not the alias
        matches = sub;
    }
    Some(path)
}
```
Gate on `canonical_path(argv)` first. Keep the current token-subsequence check as a second, fail-closed layer, and refuse (fail closed) when clap cannot parse. If you prefer to stay data-driven, emit `aliases` per path segment into the index and match against segment-or-alias. Add a test that iterates every destructive row and asserts the gate fires for every alias spelling (`models preferences reset`, `orchestrator snapshot restore`).

## Warnings

### WR-01: Gate is default-open; unclassified destructive verbs run without confirmation, and the docs overclaim

**File:** `contracts/capabilities/side-effect-ratchet.v1.json` (906 unclassified), `crates/vox-capability-registry/src/index.rs:157-163`, `docs/src/reference/gui-navigation.md` ("Destructive commands ask for confirmation, and the backend refuses to run them without it")
**Issue:** The backend gate only fires for rows classified exactly `destructive` (10 rows). Verified unclassified (`side_effect_class: null`) rows that delete data:
- `vox db prune-apply`. `db/local.rs:396` says "destructive deletes"; its sibling `vox db prune` is gated, but whole-token matching means `prune-apply` is not.
- `vox db publication-media-delete`.
- `vox ci artifact-prune`.
- `vox ci kill-stuck-tests`.
- `vox logout`.

The ratchet permits these indefinitely (it only stops the count from rising). The doc sentence presents the gate as comprehensive. MCP destructive tools are also ungated (known residual).
**Fix:** Classify the destructive verbs above in `catalog.v1.yaml` now (after reading the handlers) and make the ratchet baseline shrink on them. Reword the doc to "verbs classified destructive in the capability index (currently N of M); unclassified verbs are not gated". Consider failing closed for an unclassified verb in `execute_command`'s form path (require `confirmed` for `side_effect_class == null` rows that have required-`--yes`-style flags), or at minimum a CI test that no row whose clap about/handler mentions delete/remove/prune/reset stays unclassified.

### WR-02: No test proves `execute_command` actually calls the gate (the exact anti-pattern AGENTS.md names)

**File:** `crates/vox-gui/src/commands/execute.rs:46-59`
**Issue:** `destructive_argv_is_gated_before_spawn` re-implements the wiring (`form_argv` then `gate_execution`) rather than exercising `execute_command`. Deleting line 28 (`gate_execution(...)?;`) leaves every Rust test green. The e2e spec uses a JS-side mock that re-implements the refusal, so it also passes with the Rust call site deleted. The mutation proof in the SUMMARY was manual and is not persisted. AGENTS.md says "a validator unit-tested directly still passed with every call site deleted".
**Fix:** Extract the pre-spawn step into a function `fn prepare_argv(path, args, confirmed) -> Result<Vec<String>, String>` that `execute_command` must call (and unit-test that function), so the sidecar spawn cannot be reached without it. Alternatively add a source-assertion test (`include_str!("execute.rs")` contains `gate_execution(` inside `execute_command`'s body) as a cheap tripwire.

### WR-03: Omnibar Enter ignores the focused row and fires during IME composition

**File:** `crates/vox-gui/ui/src/components/layout/Omnibar.tsx:445-478`
**Issue:** Two bugs in the window `keydown` handler.
- `Enter` always does `e.preventDefault()` and activates `list[idx]` or `list[0]`. A keyboard user who Tabs onto the third row button and presses Enter gets row 0 (or the last arrow-selected row) activated, and the focused button's own click is suppressed. The wrong target can be a direct run.
- There is no `e.isComposing` / `keyCode === 229` check. For CJK/IME users, the Enter that commits a composition activates the first row and closes the palette. No such guard exists anywhere in non-test source.

**Fix:**
```ts
if (e.isComposing || e.keyCode === 229) return;
...
} else if (e.key === 'Enter') {
  const el = document.activeElement;
  if (el instanceof HTMLButtonElement && el.closest('[role="dialog"][aria-label="Command palette"]')) return; // let the button's click run
  ...
}
```
Better: set `selectedRowIdx` on row `onFocus` so the existing logic stays consistent.

### WR-04: Omnibar declares `aria-modal="true"` but has no focus trap and the background stays interactive

**File:** `crates/vox-gui/ui/src/components/layout/Omnibar.tsx:495-505`
**Issue:** This phase added `role="dialog" aria-modal="true"` (the base version had neither). It is a plain `div`. Tab leaves the dialog into the page behind it, and the page is not `inert`. `aria-modal` tells assistive tech that outside content is unavailable, which is false here. The sibling dialogs (Explain drawer, Confirm, Output, Sheet) do trap focus, so the primary dialog is the inconsistent one.
**Fix:** Reuse the trap from `ExplainDrawer`/`DocViewerDrawer`, or render the palette inside the Radix `Dialog` primitive already in the codebase (`components/ui/Dialog`). At minimum add a Tab handler that cycles within the dialog.

### WR-05: Index-load error is never cleared; a successful retry still shows "Capability index unavailable"

**File:** `crates/vox-gui/ui/src/hooks/useCapabilityIndex.ts:21-33`, `Omnibar.tsx:606-610`
**Issue:** `setError('capability index failed to load')` is set on rejection and never reset. `loadCapabilityIndex` correctly clears `pending` so the next open retries, but after a successful retry `mod` is set while `error` stays set. Omnibar renders `{indexError && …}` regardless of `mod`, so the banner persists for the rest of the session. During the retry itself `loading = enabled && !mod && !error` is false, so no loading line shows either.
**Fix:** In the effect, `setError(null)` before calling `loadCapabilityIndex()` and in the `.then`. Add a test: reject once, resolve on the second `enabled` toggle, assert `error === null`. The 30-line `useCapabilityIndex.test.ts` does not cover this.

### WR-06: If the dynamic import rejects, the palette loses every surface and command

**File:** `crates/vox-gui/ui/src/components/layout/Omnibar.tsx:72-83`, `omnibarFacets.ts:197-243`
**Issue:** D-05 removed surfaces and commands from the federated lane (`federatedKindsForMode` no longer includes `surface`/`command`). When the lazy chunk fails to load (offline dev server, bad chunk hash after an update), the user can only reach surfaces whose label happens to match the content manifest, and gets no CLI rows at all. The error line is the only signal, and `noMatches` shows "No matches for …" as well.
**Fix:** Fall back to `SURFACE_REGISTRY` (already imported by `useFederatedSearchIndex`) for surface rows when `indexError` is set, and say so ("Showing built-in surfaces only"). Add a unit test with a failing loader.

### WR-07: Facet "N of M" totals are capped at 200 hits across all kinds, so M is wrong and whole kinds can vanish

**File:** `crates/vox-gui/ui/src/components/layout/Omnibar.tsx:242`, `capabilityRank.ts:214`, `omnibarFacets.ts:456-463`
**Issue:** The Omnibar ranks with `limit: 200` over all kinds, then splits into facets. `total` is documented as "Uncapped row count", but it is the count of the post-slice hits. A broad query (`vox`, `a`, `db`) matches far more than 200 rows. Because the sort is by tier and score, not by kind, the 200 survivors can be dominated by one kind, so the Tools & crates or Docs facets can be empty, and "6 of 40" understates reality. D-08a promised an honest count.
**Fix:** Rank without a global limit (the pool is ~1.5k rows; the cost is already paid), and let `make()` cap per facet. Or rank per facet kind with its own limit and carry the true matched count through `RankHit[]` (for example a `RankResult { hits, totalByKind }`).

### WR-08: CommandCatalogForm: confirm binds the old args to the currently selected path, and Run has no in-flight guard

**File:** `crates/vox-gui/ui/src/components/CommandCatalogForm.tsx:101-119, 285-295`
**Issue:**
- `pendingConfirm` stores `{id, args}` but not the path. `onConfirm` re-runs `currentCommand.path` with `p.args` and `confirmed=true`. If the user selects a different command between the click and the (async) refusal arriving, the refusal sets `pendingConfirm` for the old command's args, the dialog names the new `selectedPath`, and Confirm sends the old args with `confirmed: true` to the new path. The window is short but `run` has no staleness check on either `setOutput` or `setPendingConfirm`.
- `handleExecute` can be clicked repeatedly while the first `executeCommand` is pending, so a side-effecting verb runs twice. There is no disabled/pending state.

**Fix:** Store `{id, path, args}` in `pendingConfirm` and call `run(p.path, p.args, true)`. Track a run token (`useRef`) and drop results whose token is stale. Disable Run while a run is pending.

### WR-09: Direct palette run has no progress, timeout, double-run guard, or output bound

**File:** `crates/vox-gui/ui/src/App.tsx:1044-1063`, `crates/vox-gui/src/commands/execute.rs:30-43`, `RunOutputDialog.tsx:22-27`
**Issue:** The palette closes on Enter. A slow read-only verb (several `vox ci … verify` and `vox db verify` can take minutes) gives no feedback until it finishes, and re-opening the palette and pressing Enter again starts a second concurrent run. `execute_command` buffers all stdout/stderr (`.output().await`) with no cap or timeout, and `RunOutputDialog` renders the whole string in a `<pre>`, so a multi-MB output freezes the UI.
**Fix:** Push an "info" toast `vox <cmd> — running…` immediately and dedupe in-flight runs by path. Cap the captured output (for example 1 MiB with a "truncated" marker) in `execute_command`, and cap what `RunOutputDialog` renders with a "show more" control.

### WR-10: A failed or late initial keybind load pins defaults, and the next rebind overwrites the user's persisted bindings

**File:** `crates/vox-gui/ui/src/lib/keybindStore.ts:17-24, 33-38`, `SettingsView.tsx` capture handler
**Issue:** `load()` sets `loaded = true` before the request and swallows a rejection, so a transient backend failure at startup is never retried. The snapshot stays at `DEFAULT_BINDINGS`. The Settings capture then does `next = { ...keybindings, [id]: chord }` from that snapshot and `setBindings(next)` persists the full object, silently replacing the user's saved custom bindings for every other action. The previous per-mount code at least retried on each mount. `setBindings` also swallows persist failure while the UI claims the change is saved.
**Fix:** Reset `loaded = false` on rejection so the next subscriber retries. In `setBindings`, persist only when the initial load has succeeded, or merge the delta (`{[id]: chord}`) into the freshly loaded value. Surface a persist failure to Settings.

### WR-11: `#` / `>` / `/` with an empty query show "Submit new task…" and Enter activates it

**File:** `crates/vox-gui/ui/src/components/layout/Omnibar.tsx:309-321`
**Issue:** `withSubmitTask = effectiveQ.trim() ? agentRows : [...agentRows, SUBMIT_TASK_ROW]`. In `#` mode (D-10: crates only), typing just `#` gives an empty `effectiveQ`, so the Commands facet shows "Submit new task…" as the only row, and Enter (no selection means `list[0]`) triggers `onSubmitTask`. The same happens in `>`, `/` and `@` modes.
**Fix:** Add the row only when `prefixMode === 'default'` (the comment says it is the empty-landing-state suggestion).

### WR-12: A non-string value in the stored `gui.keybinds` JSON crashes App render

**File:** `crates/vox-gui/ui/src/lib/keybinds.ts:42-52, 87-93`
**Issue:** `parseBindings` returns `{...DEFAULT_BINDINGS, ...JSON.parse(json)}` without validating value types. `paletteActionRows`/`ShortcutSheet` call `formatChord(bindings[id] ?? DEFAULT)`, and `formatChord` calls `chord.split('+')`. A stored `{"open-palette": 5}` (corrupt or hand-edited preference) throws `chord.split is not a function` during App render, a white screen on every launch, and the only fix is editing the backend preference. `App` renders `paletteActionRows` unconditionally.
**Fix:** In `parseBindings`, keep only entries where `typeof v === 'string'` and the key is a known action id; fall back to the default for the rest.

## Info

### IN-01: Stale palette prefill re-applies every time the Catalog surface remounts

**File:** `crates/vox-gui/ui/src/components/CommandCatalogForm.tsx:67-74`, `App.tsx` (`catalogPrefill` state)
**Issue:** `catalogPrefill` is never cleared. The `[nonce]` effect also runs on mount, so leaving Catalog and returning re-selects the old palette command and discards what the user picked meanwhile. If the catalog hasn't loaded yet when the prefill applies, `handleCommandSelect` finds no entry and skips seeding defaults.
**Fix:** Clear the prefill after applying it (callback prop) or track the last applied nonce in a ref; re-seed when `commandList` arrives.

### IN-02: Run output `<pre>` is a scroll region that keyboard users cannot reach

**File:** `crates/vox-gui/ui/src/components/layout/RunOutputDialog.tsx:22-27`
**Issue:** `overflow-auto max-h-[30vh]` with no `tabIndex`, and `aria-label` on a bare `<pre>` (no role). Keyboard-only users cannot scroll long output (WCAG 2.1.1).
**Fix:** `<pre tabIndex={0} role="region" aria-label={stream}>`.

### IN-03: `?` guard gaps and IME

**File:** `crates/vox-gui/ui/src/lib/keybinds.ts:68-73`
**Issue:** `isEditableTarget` checks tag and `contenteditable` only. It misses `role="textbox"`/`combobox` on non-inputs, and for inputs inside an open shadow root `e.target` is retargeted to the host, so a `?` typed there opens the sheet. No `e.isComposing` check. Today the only `role="textbox"` elements in the app are real `<input>`s, so this is latent. Also `[contenteditable="false"]` is treated as editable (fails safe).
**Fix:** Use `e.composedPath()[0]` and add `[role="textbox"],[role="combobox"],[role="searchbox"]` to the `closest()` check.

### IN-04: `normalizeQuery` does not collapse internal whitespace

**File:** `crates/vox-gui/ui/src/lib/capabilityRank.ts:101-104`
**Issue:** `vox  fabrica  fmt` (double spaces) misses the tier-0 exact alias and drops to tier 2.
**Fix:** `.replace(/\s+/g, ' ')` after `trim()`.

### IN-05: Graph lane: stale neighbor append and wasted calls in `#` mode

**File:** `crates/vox-gui/ui/src/components/layout/Omnibar.tsx:268-293, 391-415`
**Issue:** `expandGraphNeighbors` has no cancellation, so a slow `vox_search_neighbors` response appends rows from the previous query into the new query's graph facet. The discover effect also fires `vox_search_structural` for `#` queries whose graph rows are silenced by `buildOmnibarFacets`.
**Fix:** Guard on a request id; skip the MCP call when `prefixMode === 'crates'`.

### IN-06: Class strings are free-form in the index schema and compared literally

**File:** `contracts/capabilities/capability-index.v1.schema.json:115` (`nullable_string`), `index.rs:159`
**Issue:** Only `catalog.v1.schema.json` enumerates `side_effect_class`. The index schema and the Rust gate accept any string; an unknown value is treated read-only-ish by the Rust gate (not gated) but fail-closed by the TS `isReadOnlyClass`. The two sides disagree on unknowns.
**Fix:** Add the same enum to the index schema, and make `confirmation_required` treat any value outside the known set as gated (or fail the generator).

### IN-07: Stale doc comment and naming

**File:** `crates/vox-gui/ui/src/lib/omnibarFacets.ts:101` (`cli` activation: "nothing is executed" is no longer true), `App.tsx` (`catalogPaths` is built from `data.skills`, which is the CLI catalog, not skills)
**Fix:** Update the comment; rename to `cliCatalog`.

### IN-08: Omnibar results have no listbox semantics

**File:** `crates/vox-gui/ui/src/components/layout/Omnibar.tsx:508-595`
**Issue:** The input lacks `role="combobox"`/`aria-controls`/`aria-activedescendant`, and rows are plain buttons marked only with `aria-current`. Screen-reader users do not hear the arrow-key selection.
**Fix:** Give rows ids and `role="option"` inside `role="listbox"`, and point `aria-activedescendant` at the selected row.
