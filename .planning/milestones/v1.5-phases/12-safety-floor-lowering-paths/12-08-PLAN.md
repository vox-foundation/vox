<objective>
Make the two MCP-protocol entry points vox controls, the HTTP gateway and the stdio `vox mcp` server, agent-origin by construction, so neither can approve or modify a floored park (revision-3 ruling, split out of 12-07).

Purpose: 12-07 adds the `AGENT_ORIGIN` task-local, `refuse_agent_floor_resolution` in the resolve arm, and the two in-process dispatcher wrappers. External MCP clients reach the same resolve arm through these two entry points, and only agents use them to approve:
- **HTTP gateway.** `/ln`, `/v1/tools/call` and `/v1/ws` dispatch in-process through the single `call_tool_json` (rpc_tools.rs:113), which gets the same wrapper. The GUI never uses the gateway. Its one human surface is the gateway's own `/v1/mobile` page, a free-form tool console with no approval affordance. On the wire it cannot be told apart from a bearer-holding MCP-HTTP agent, so any "I am human" flag there would be forgeable by every gateway client. The gateway is therefore agent-origin in full. The mobile console can still reject, and the human channel for floored approvals is the GUI inbox (T-12-29).
- **Stdio server.** It forwards every call over the daemon's `orch.tool_call` (server.rs:369 → daemon_route.rs:29), the same method the GUI uses. The forwarder adds `params.agent_origin: true`, and the daemon's TOOL_CALL arm enters `with_agent_origin` when the flag is set.

This flag route was chosen over refusing in server.rs before forwarding:
- The refusal is enforced once, in 12-07's resolve arm, against the daemon's real pending entry. There is no second copy of the decision/approval-id parsing or the floored predicate in another process.
- It avoids a list-then-resolve window, which guessable approval ids would make exploitable.
- It covers every forwarded tool, not only `vox_resolve_approval`.
- The flag can only add a restriction. The client LLM composes only `args`, never the params object around it, so the only bypass is omitting the flag. That requires composing raw daemon RPC with the daemon token, which is the narrowed residual below.
- A top-level `DispatchRequest` field like `permission_mode` would buy nothing (the threat is omission, not injection) and would touch vox-foundation plus about 25 struct literals.

Out of scope, recorded as an accepted residual (T-12-25): a raw daemon-socket or token-holding local process can still omit the flag or call `orch.resolve_approval` and look human. This includes an agent that shells out (e.g. `vox_run_shell`) to open the socket or gateway itself. Its owner is FLOOR-04b and Phase 14 success criterion 5: "only the authenticated human channel can approve/modify a floored park".

Output:
- a one-line gateway wrapper;
- the stdio flag, and the daemon honouring it;
- call-site tests for the gateway and the stdio forwarder;
- a source-scan test pinning every caller and daemon client;
- one sentence of contract text.
</objective>
