<objective>
Stop an agent from approving its own floored park (research OQ4, orchestrator ruling on the revision-1 BLOCKER).

Purpose: the phase goal is that floored actions always require a human. Today any caller of `vox_resolve_approval` resolves any park, so a sub-agent or a chat model steered by prompt-injected tool output can park a floored call and approve it on the next turn. Every origin converges on `dispatch_tool_call`, which cannot tell a human from an MCP client by anything on the wire. Two origins, though, are vox's own in-process code: the chat agent loop (`run_agent_turn` calls `handle_tool_call_with_receipt` at agent_loop.rs:976) and the autonomous runtime bridge (`McpToolDispatcher::dispatch` calls `handle_tool_call_with_mode` at autonomous_tool_dispatch.rs:78). Those two call sites enter a task-local "agent origin" scope, and the resolve arm refuses approve/modify of a floored park inside it. Nothing a client sends can leave that scope.

Out of scope here: the MCP-protocol entry points (the stdio `vox mcp` server and the HTTP gateway) become agent-origin in 12-08, which builds on this plan's scope and refusal. The raw daemon-socket / token-holder residual (T-12-25) is recorded there.

Output: about 40 lines in floor_gate.rs, a 3-line refusal in the dispatch.rs resolve arm, and a one-line wrapper at each in-process dispatcher. Also: call-site tests for both dispatchers, a GUI-path positive test, and OQ4 marked resolved in 12-CONTEXT.md.
</objective>

- The `vox_resolve_approval` arm (dispatch.rs:735) reads `approval_id` and `outcome`/`decision`, maps the decision with `pending_approvals::outcome_from_decision` (anything other than approve/modify becomes `Rejected`), and calls `state.pending_approvals.resolve`.
- The GUI resolves through `voxTransport.invokeMcpTool('vox_resolve_approval', …)` (useAttentionInbox.ts:57, useAgentApprovals.ts:46). That reaches `daemon_extra.rs:191` `handle_tool_call_with_mode`, which runs outside any agent scope. The separate `orch.resolve_approval` RPC (daemon_extra.rs:231) calls `pending_approvals.resolve` directly and never enters dispatch.
- vox-cli has no approval-resolving command.
- Non-test `handle_tool_call*` callers outside dispatch.rs's own delegation chain: `autonomous_tool_dispatch.rs:78`, `chat_tools/chat/agent_loop.rs:976`, `daemon_extra.rs:191`, `http_gateway/rpc_tools.rs:114`. Every other hit is inside an inline `#[cfg(test)] mod … {` block that ends its file (receipt_tools.rs:61, scope_guard.rs:59, dispatch.rs:2058).
- No `tokio::spawn` sits between `handle_tool_call*` entry and the resolve arm, so a task-local set around the dispatcher call is visible in the arm.
- Re-parked approvals after a restart get the summary `[recovered-on-restart] {tool}` (hitl_rehydrate.rs:140), which drops the `[floor:<id>]` prefix.
- The workspace `tokio` features include `rt`, which provides `tokio::task_local!`; no dependency change.

Mutation-safety rule (12-04): every park in these tests uses `vox_skill_install {}` under `accept_all`. It floors as ExternalEffect, parks before argument parsing, and if approved fails argument validation without installing anything.
