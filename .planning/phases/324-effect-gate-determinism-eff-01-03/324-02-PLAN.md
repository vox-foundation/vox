# Phase 324 Plan 02: Runtime Python capability refusal

<objective>
Close verification truth 4 (EFF-02 runtime clause, roadmap success criterion 3). `CapabilitySet` already parses `py:allow` and `py:unverified`. No production interpreter path consults those grants. When the interpreter is about to run a user function whose declared `HirCapability` is `Python` or `PythonUnverified`, refuse with the existing `EvalError::CapabilityDenied` unless the granted set allows the matching namespace.

324-01 already shipped D-01 (shared effect-item parser), D-02 (`python` / `python_unverified` effects), D-03 (effect compliance; Tier 1 module names stay in phase 326), D-04's caps grammar (`py:allow` grants `py`, `py:unverified` grants both, `developer_default()` still allows every gated namespace), and D-05 (workflow determinism lint). Leave that work in place.

D-04's last sentence defers an actual bridge call to phase 325. This plan does not build that worker. The deferred idea is the bridge call. The gap is the caps check on the declared effect. Phase 325 owns `crates/vox-python-bridge`.

Purpose: a later Python builtin must not be able to run under `vox run --caps` that omits `py`.
Output: interpreter denial before the body, plus tests that fail when `allows_namespace("py")` is removed.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| vox run --caps → interpreter | The granted CapabilitySet is the receiver's authority. A user function body is untrusted relative to that grant. |
| Lowered HirFn.capabilities → call | The effect is whatever HIR recorded at registration. A runtime object field is not a grant. |
