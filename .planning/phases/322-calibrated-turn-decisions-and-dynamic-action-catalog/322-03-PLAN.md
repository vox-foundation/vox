<objective>
Ship ChatARC: one lexical shortlist over skills, MCP tools and commands, one calibrated Choice over it (including none), and three consumers that reuse existing control points (CAT-01, CAT-02).

Purpose: a new skill, tool or command becomes reachable in chat without registration code, and a chat turn can act on it only when the choice is calibrated to be right.

Output: `chatarc.rs` with tests, `SkillSearchIndex::from_docs`, the skill / tool / command consumers in the chat path, a command-hint provider seam registered by vox-cli, hermetic fixtures, held-out metrics appended to `322-EVAL-REPORT.md`, and where-things-live rows.

Operator-locked decisions (continuing 322-01's numbering):
L-05 compose three existing sources (skill registry; TOOL_REGISTRY as filtered by select_tools_for_turn; command_catalog::build_catalog only through a runtime provider seam set by the binary hosting the chat server); no new crate edge, no third registry, no closed-world enum of actions.
L-06 shortlist is lexical top-K, K ≤ 10 including none, reusing an existing lexical scorer reachable from vox-orchestrator-mcp; no bespoke index.
L-07 consumers: skill → existing pinned-skill injection with trigger_source "chatarc", only without an explicit pin; tool → TurnContext.pin_names in run_agent_turn; command → one hint line in the system prompt.
L-08 fail open: below threshold, none, flag off, or provider unset is exactly today's behaviour.
L-09 get_skill_reliability stays the install gate; list_skill_reliability may be read only as a prior.
L-10 discovery: a new skill, tool or command appears on the next pass; test each.
L-11, L-12, L-15 as in 322-01.

Choices made under Claude's discretion:
- Scorer: `SkillSearchIndex` (src/skill_search_index.rs, BM25) gains `from_docs(impl IntoIterator<Item = (String, String)>)` and `from_manifests` delegates to it. `tool_search.rs::rank_tools` is not reused: it is bound to TOOL_REGISTRY and its scores are not comparable across sources.
- Reliability prior (L-09 "may"): not read. RESEARCH F8 and chat_tools/mod.rs record that nothing writes skill reliability rows yet, so the prior would be a constant with no effect. Add it when a producer exists.
- The index is rebuilt per turn from the live sources. That is what makes discovery immediate; cost is a few hundred short documents per turn behind a default-off flag. Mark it with a `ponytail:` comment (per-turn rebuild; cache keyed on source generation if profiling shows it).

**Provider-seam location and a recorded gap (operator decision needed, not planned around):**
The seam lives in `crates/vox-orchestrator-mcp/src/chat_tools/chatarc.rs` (`register_command_hint_provider`, the vram.rs `register_vram_probe` idiom) and vox-cli registers it at the top of `main()` in `crates/vox-cli/src/main.rs` (vox-cli already depends on vox-orchestrator-mcp; the reverse edge would break the layer rule). On this branch the production chat host is not vox-cli: `vox mcp` forwards `vox_chat_message` to `vox-orchestrator-d` (`daemon_route.rs`, `call_tool_via_daemon`), the GUI calls the daemon too, and `vox-orchestrator-d` does not depend on vox-cli. Registering there would need a new crate edge (USER-AUTHORIZED-ONLY) or a subprocess call to a PATH-resolved `vox commands --json` (a new exec trust boundary). Neither is planned. Consequence: in daemon-hosted chat, command candidates fail open to none (L-08), while skills and tools work; commands work in in-process hosts such as `vox harness eval` live runs (`crates/vox-cli/src/commands/harness/live_eval.rs`). Record this in the SUMMARY and the report.
