<objective>
Build the agent spoke's behavioral suite (TOP PRIORITY, SPOKE-06) and prove, without any model, that
it discriminates (D-07, D-08, D-10). Plan 338-08 runs it on models.

**Ordering (D-15):** start only after phase 335 has landed (it edits `crates/vox-eval`) and after plan
338-02 (both register modules in `crates/vox-eval/src/lib.rs`; this plan is wave 3 for that file only).
The executor re-reads vox-eval's lib.rs and reasoning_slice.rs (`mcnemar_one_sided_p`) at execution
time.

**Hosting (D-14, D-21):** pure types, scorer, mock world and controls live in vox-eval with no new
dependencies; the JSON-Schema validator is injected as a function so vox-eval stays dependency-free
(plan 338-08 supplies it from vox-jsonschema-util in vox-ml-cli). The catalog export lives in
vox-orchestrator-mcp, which owns the live registry; vox-ml-cli reads the committed file as data. No new
crate edge (option B, a vox-ml-cli -> vox-orchestrator-mcp edge, is not used).

Expected wall-clock (D-16): no GPU and no model. All tests here are unit tests, seconds each after the
crates build.

Limitation stated in the README: "refuses" is detected as "did nothing out of scope and said something",
not as a correct explanation.

Purpose: the agent spokes get a gate that measures what a harness model must do, from outcomes.
Output: catalog export plus drift test, episode runner and scorer, 72 episodes, controls, SuiteReport,
suite_verdict, authoring guide.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model output -> episode runner | model text is parsed into tool calls; untrusted |
| episode runner -> tools | calls must never reach real tool handlers |
| live registry -> committed catalog | the catalog must reflect the registry, or the gate measures stale schemas |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-338-11 | Elevation / Tampering | episode execution | high | mitigate | `run_episode` executes calls only against the episode's scripted world; vox-eval has no dependency on any tool handler, so a real dispatch cannot be linked in; the runner never calls `handle_tool_call_with_receipt` |
| T-338-12 | Tampering | tool-result content injected into the next prompt | low | accept | results are authored fixture data, not live output |
| T-338-13 | Information Disclosure | eval leakage: request text reveals the answer, or episodes enter training | medium | mitigate | load-time check refuses tool names and 4-word description runs in requests; README marks episodes held out; plan 338-08 extends the training leakage precondition to episodes |
| T-338-14 | Repudiation | stale catalog keeps a gate passing after a schema change | medium | mitigate | `tool_catalog_lock` regenerates from the live registry and fails on drift; plan 338-08 pins the catalog BLAKE3 in the gate policy so a regenerated catalog changes policy_blake3 (needs re-gate) |
| T-338-SC | Tampering | npm/pip/cargo installs | low | accept | no package installs; xxhash-rust, serde_json and jsonschema are existing deps |
</threat_model>
