Choose each adapter's gate policy from its spoke (D-03, SPOKE-03) and record the spoke on the adapter
card, the receipt and the Hub card without changing repo ids (D-01, SPOKE-05). The spoke is derived from
the training-lane histogram via `include_lanes` (D-19).

**Ordering (D-15):** start only after phase 335 has landed and plans 338-02 and 338-03 are done.
`eval_gate/run_gate.rs`, `populi/train_arm.rs` and `hub_sync.rs` are shared with 335 and with earlier
338 plans; the executor re-reads them at execution time.

**Locked decision over research (D-19):** research suggested omitting rows for spokes that do not apply
to an adapter. D-19 is locked: every gated spoke appears with state not_run, so a card can never imply a
spoke was checked. This plan keeps all rows and marks only derived ones as applying.

D-14: reuse `DomainProfilesFile`, `MixConfigSchema.include_lanes`, `read_training_lineage`; test-first;
no new crate edge (vox-ml-cli already depends on vox-populi and vox-corpus).

Expected wall-clock (D-16): no GPU. Spoke-routed eval-gate on an existing run dir only reads reports,
seconds per run.

Purpose: promotion consults the gate for what the adapter was trained to do, and every surface says
which spoke that is.
Output: spoke derivation, spoke-routed eval-gate, spoke fields on adapter card, receipt and Hub card.
</objective>
