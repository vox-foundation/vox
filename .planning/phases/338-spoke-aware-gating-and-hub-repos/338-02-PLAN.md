<objective>
Retargeted by 339-01: the card code lives in `hub_card/facts.rs` (state) and `templates/hub/` (words); see its 338 retarget table.

Make receipts hash their inputs and the gate policy so a pass under a retired rule reads
`needs re-gate` (D-05, D-06, SPOKE-04), and publish the versioned per-spoke gate state and receipt
schemas that phases 339 (cards v2) and 340 (local selector) consume (D-17).

**Ordering (D-15):** start only after phase 335 and phase 337 have landed (337 may add the decode
settings record this plan hashes). This plan edits `eval_gate/run_gate.rs` and `eval_collateral.rs`,
which 335 edits; the executor re-reads them at execution time and works from their landed shape.

**Interface for 339/340 (D-17):** `contracts/mens/spoke-gate-state.v1.schema.json` (file
`spoke_gates.json` in a run dir and in a published bundle) and `contracts/mens/gate-receipt.v2.schema.json`
(files `gate_receipt.json` and, from plan 338-06, `gate_receipt.<spoke>.json`). The four states are
`passed`, `failed`, `needs_re_gate`, `not_run`. 339 and 340 read these files and must not re-derive
state from receipts themselves.

D-02/D-04/D-10 are enforced in the state function. D-14: hashing goes through vox-crypto in the
callers (vox-eval has no vox-crypto edge and gets none); test-first; no new crate edge.

Purpose: a receipt cannot keep vouching for weights or a rule it did not judge.
Output: `vox_eval::gate_state`, receipt schema 2, `spoke_gates.json`, two JSON Schemas, per-spoke card
table.
</objective>
