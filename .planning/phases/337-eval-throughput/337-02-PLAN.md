Wire the protocol identity from 337-01 through the host and the plugin load (THRU-07, and the
"protocol in key" part of THRU-09): checkpoint inputs, the report `decode` object 338 hashes, the
baseline-pairing refusal, and a plugin that refuses numerics it does not implement (D-05, D-07, D-24).

**Ordering (D-14, D-26):** start only after phase 335 has landed. This plan edits `item_checkpoint.rs`,
`reasoning_eval.rs`, `eval_collateral.rs`, `reasoning_compare.rs` and `baseline_from_compare.rs`, which
335 is changing; the executor re-reads each at execution time and works from its landed shape, not from
the line numbers quoted here. This plan and 337-03 are what phase 338 needs from 337 (D-15); their
SUMMARYs should exist before 338-02 starts.

**Key stability is the hard constraint.** `hash_json` hashes `Value::to_string()`, and serde_json's
`preserve_order` is on workspace-wide, so the key depends on field insertion order (the comment on
`hash_json` that says keys are sorted is wrong; correct it). The f32 inputs literal stays byte-for-byte as
it is; protocol fields are appended after it only for bf16. `REASONING_SCORER` and `model_identity` are
not touched (research: changing either orphans every cached generation).

Purpose: a generation, a report and a baseline each say which numerics produced them, and the gate
cannot pair two different ones.
Output: golden-key test, `decode` objects in both reports, the baseline refusal, plugin load refusal,
mutation proofs; the SUMMARY states the 338-02 amendment (decode_blake3 hashes this `decode` object,
which has no batch size).
</objective>
